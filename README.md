# TernMate

TernMate 是 [Tern](https://docs.stencil.so/tern/guides/blocks.html) 的 GitHub Issue / PR 工作台。在项目窗口里筛选任务，单击或按 `Enter`，即可在对应代码目录启动或恢复交互式 `omp` 会话，无需复制链接或补写提示。

## 安装

在 Tern 宿主机上准备 `tern`、`git`、`gh` 和 `omp`（可使用 Tern 随附的 `omp`）。使用 `gh auth status` 确认已登录；未登录时运行 `gh auth login`。读取 GitHub Actions 日志还要求 `gh api --help` 中列出 `--allow-escape-sequences`。

macOS 上 Tern 宿主的 `PATH` 可能与终端不同。TernMate 在宿主 `PATH` 之后查找 `/opt/homebrew/bin` 和 `/usr/local/bin` 中的 `gh`。若安装在其他目录，请将其加入 Tern 宿主的 `PATH`，而不只是 shell 的启动配置。

```sh
git clone https://github.com/gulanthys/TernMate.git
cd TernMate
tern plugin link .
tern plugin list
```

## 使用

1. 在 Tern 命令面板选择 **New TernMate**，工作台在当前 session 的来源面板右侧分屏打开。顶部显示任务仓库和本地路径。若有多个候选（如 fork 和上游），先选 `owner/repo`；之后可从 **仓库** 菜单切换目标或选 **本地 checkout…**。仓库发现使用来源面板的工作目录，不读取 `omp --cwd`。
2. **开发模式**保留 Issue / PR 列表和 **新建 Issue**。按 `Tab` 切换 Issue / PR，按 `/` 搜标题，或用 **快捷筛选** 和 **筛选**。筛选覆盖整个本地镜像，不限于当前页；`R` 主动同步。
3. **审核模式**只列开放、非草稿 PR，不限于请求我审查。可再按审查请求、线程或 CI 等条件筛选。没有新建 Issue 或复制推送命令入口。
4. 两个模式分别保留筛选和选中位置。任务列表按面板高度分页，不用滚动。按 `↑` / `↓` 选择，按 `←` / `→` 或点击底部按钮翻页，单击或按 `Enter` 打开对应的 omp tab；同一身份、checkout、模式和版本再次打开时，聚焦或恢复原会话。
5. **新建 Issue**支持本地草稿、查重、预览和明确确认；不支持的模板走 GitHub 原生入口。多窗口同时编辑时不会覆盖新版草稿，未保存的输入会留在编辑器供核对。仓库访问无法重新确认时，不读取原账号的草稿。发送使用经核对的同一账号凭据；仓库可见性变化后须重新预览。创建成功或首次关联网页原件后自动刷新列表，保留筛选和选中项。发送前校验失败可继续编辑；请求可能已发出但结果未知时只能核对回执，不能重发。模板解析和提交存储使用宿主的 `/usr/bin/ruby`。

选中 Issue 的进度与分页控件同在底部，列表使用上方空间。

开发模式的开放 Issue / PR 标签显示当前仓库的开放数量，不受列表筛选影响。要查看所有状态，使用 **快捷筛选 → 全部状态**。
Issue 和 PR 列表按编号从大到小排列，审核模式也一样。
点「刷新」或按 `R` 后，最新创建的 Issue 和 PR 会优先核对；扫描中再次刷新，会在本轮结束后再查一次。已核对的变化先显示，不等仓库历史全部扫完。未核对的旧行暂时保留；若扫描失败，重试也保留两种列表中已经核对的行，直到新证据更新它们。完整扫描成功后才显示准确总数。
只有最近一次同步成功、覆盖完整且没有待判定匹配项时，分页才显示「共 N 项」。同步中、失败或过期时仍可浏览已知行，分页显示「已找到 N 项」；仓库标签用「上次 N」标明旧的完整计数。

一条 PR 只显示一行；开放、草稿、已合并或关闭未合并的状态，与合并冲突、当前 head 的 CI 失败、未解决线程和请求我审查等信号并列，不互相覆盖。
开发和审核 PR 列表均标注 Issue：合并后关闭的 Issue，以及正文中由 GitHub 确认为 Issue 的引用（例如“关联 #522”）。同仓显示 `Issue #编号`，跨仓显示 `Issue owner/repo#编号`，多个关联去重并列；正文引用不代表合并后自动关单。GitHub 标为 PR 的引用（例如“拆自 #1241”）不会误标成 Issue。未发现明确关联与关联未完整核对分别提示，不从标题或分支名猜测归属。正文只临时读取以提取编号／URL，不写入镜像。

Issue 和 PR 都直接按 OMP 的正常配置加载审批模式。TernMate 不修改全局配置、不逐个 PR 强制审批，也不自动批准工具调用；如果 OMP 的有效配置要求审批，仍会提示。

PR 会话禁止从 worktree 自动加载规则、上下文文件、技能、扩展和自定义系统提示，项目 MCP 也保持禁用。每次新建或恢复 PR 进程时，TernMate 通过所用 `omp config path` 找到当前用户配置目录，只把其中的 `RULES.md`（如有，须为普通文件而非符号链接）连同任务边界传入系统提示。全局规则不会授予远端写入权限，也不是命令级拦截器。

复用符合当前权限边界的运行中会话时不重启。升级前使用通用读取工具的审核会话不会被工作台聚焦或恢复；再次打开同一 PR 会新建受限审核会话，不改动旧面板或历史。旧进程的权限不会自动收紧，应正常退出。其他 PR 会话退出再恢复时使用新的全局规则。

首次启动失败时，若工作台能确认该进程已退出且未留下会话文件，可再次点击同一任务重试。不能确认时保留旧面板和记录，不创建替代会话。

旧版未绑定稳定身份的会话不会从工作台自动恢复。再次打开任务会在独立工作区另开会话；旧对话、旧 worktree 和原 checkout 的修改不会被迁移或删除。

Issue 列表并列显示 GitHub 状态（开放、重新开放、关闭及原因）、本机会话记录，以及 GitHub 明确关联的 PR（草稿、待合并、已合并、关闭未合并）。PR 已合并而 Issue 未关闭时会单独提示。选中 Issue 后会列出各个关联 PR（跨仓显示 `owner/repo#编号`），并核对本机任务 worktree 的提交、未提交改动或不可核对状态。子模块内部改动未核对时，不显示为干净。会话打开不等于有人认领，合并或关闭也不等于验收；关联未核对完整时不判定无关联，不自动写 GitHub。

首次选仓需在线核对仓库和账号并建立本机镜像。再次打开先读该身份的镜像；全量历史约每 5 分钟后台核对。显示开发或审核 PR 列表时，另外约每 30 秒轻量核对开放 PR 的 head、CI、审查和线程，并补查本地已知开放 PR 的合并／关闭变化，不反复扫描全部历史。进入 PR 列表、返回工作台时也触发在线核对，短时间重复聚焦合并；全量扫描与轻量核对不并发，失败或限流时退避并保留旧数据。这是轮询，不是 GitHub 实时推送。轻量核对不冒充全量镜像的新鲜度，不写镜像；完整核对成功才保存镜像核对时间。关闭工作台不运行常驻服务。镜像仅保存列表及维护所需的元数据，不包含任务正文、讨论或 CI 日志。

| 任务 | 打开后的行为 |
| --- | --- |
| Issue | 从所选 checkout 的已提交 `HEAD` 创建独立 worktree 和 `ternmate/issue-<编号>-<标识>` 本地分支。`omp` 在该目录只读分析正文、讨论和代码；明确要求修复后才修改。原 checkout 的未提交内容不带入。 |
| 开发模式 PR | 核对 PR head SHA 后在独立 worktree 打开。首次打开时，OMP 逐项分析 Conversation 评论、整体 review 正文和未解决的行内线程，并核对当前版本的 CI 失败。可在本地修复和验证；不会自动推送、评论、解决线程、批准或合并。 |
| 审核模式 PR | 按目标分支名、base SHA 和 head SHA 固定审核版本。OMP 使用专用只读工具查看差异、评论和固定版本源码，不能借通用读取工具访问宿主文件或 URL。结论只在对话中给出；要修复请回开发模式。 |

普通打开按所选 checkout 的 HEAD（Issue）或实时核对的 PR 版本进入当前会话。审核即使 head 不变，改投目标分支或目标分支前移也使用不同审核版本。若准备或确认期间版本又变化，会重新提示，不替用户改选。此时可选择提示中的版本，也可点 **取消** 或按 `Esc` 返回原列表，不启动会话。打开新版本或关闭工作台不会关闭旧 omp 面板、删除对话或改动旧 worktree。**worktree 不是沙箱**：不要在带凭据的环境中运行不可信 PR 的脚本。

再次点击同一版本的 PR 会在原会话中逐条分析新增的 Conversation 评论、整体 review 正文与未解决线程回复。正在处理时排队；首次材料已完整纳入的评论不会重发，因大小上限未纳入的评论仍可投递。评论读取不全会提示，不当作没有新增。若原 OMP 进程在此功能升级前已启动，请正常退出一次并从工作台重新打开，原对话和 worktree 保留。明确选择旧 PR 版本时不读取当前评论。

### 一个 Issue 拆成多个修复 PR

在开发会话中明确提出“把 A、B 拆成独立分支，分别提 PR，保留原工作区”。Issue 本身仍默认只读；只有明确要求修复或拆分后才创建分支。开发模式 PR 会话也支持将原先混在一起的修复拆开；审核模式仍只读。

OMP 使用 TernMate 的 `split-worktree` 助手，在该任务私有目录的 `fixes/<名称>` 下创建独立 worktree 和带任务编号的分支。每个修复从核对后的目标分支提交 SHA 起步，不默认从混合了 A、B 的旧实现 tip 起步；确需叠加 PR 时单独说明。原任务分支、已提交和未提交内容保持原样，只把属于该修复的改动迁入对应新工作区。已存在的目录或分支不会覆盖。每个工作区可分别验证、提交；推送和创建 PR 仍须明确指定目标和动作。

功能升级前已经运行的 omp 需要正常退出一次，再点击原任务恢复原对话，新的拆分边界才会生效。只聚焦旧进程不能改变其系统边界。选中 Issue 后会提示有拆分修复工作区；存在这些工作区时，自动清理会保留原任务和各拆分分支，避免把未完成或尚未发布的修复一起清理。

要手动推回 PR，先在独立 worktree 提交改动，再从对应 PR 的右键菜单选择 **复制推送命令**。TernMate 实时核对源仓库（含 fork）、源分支和远端 head；只有本地提交可快进时才复制指定提交和分支的命令。核对目标后自行执行；复制不会写 GitHub、设置默认远端或强推。

清理已合并 PR：在 **开发模式 → PR → 快捷筛选 → 已合并**，右键该 PR，选择 **清理本地工作区…**，核对路径后确认。每次只清理所选的开发或审核 worktree 及任务分支。远端必须仍为已合并，本地 HEAD 必须与合并的 PR head 一致；会话仍在运行、存在本地提交或有任何未提交／未跟踪／忽略文件时不清理。旧 head、原 checkout、远端分支、会话、材料和私有对象库都保留。之后打开同一版本时可以从保留的对象库重建工作区并恢复原会话。

同一筛选下也可用工具栏的 **批量清理…**。它检查当前筛选的所有页（不是只清这一页），预览符合条件的工作区和跳过原因。确认后逐项重新核对；某项不再符合条件会跳过，其他项继续，结束后显示逐项结果。

工作台在一次完整同步成功后自动清理终态任务：已合并或关闭未合并的 PR、已关闭的 Issue。先排除已没有本地工作区的任务，再在线核对终态；运行中、工作区有改动或证据不足的任务会保留。Issue 有本地提交时，只有本机 Git 能证明分支 tip 包含在此次在线核对时仍明确关联、已合并的同仓 PR head 中才清理。清理后保留原对话和可恢复的提交，不改 GitHub 或原 checkout 的工作区。

PR 和 Issue 的清理都跳过含子模块的工作区，不读取子模块内部状态或执行其 Git filter。

在 Issue 或 PR 列表工具栏点击 **自动清理历史**，可分页查看当前仓库、当前 GitHub 账号下已自动清理的分支。每条记录显示清理时间（UTC）、Issue 或 PR 编号、完整分支名和提交 SHA 前缀。重开工作台仍可查看；清理中断后，可确认分支已删除的待记记录会补入历史。手动清理、跳过项和此功能加入之前的清理不计入。

镜像、草稿和会话按 GitHub 主机、稳定仓库 ID 和稳定账号 ID 分开。检测到身份失效时，工作台关闭旧草稿面板并停止后续读写，不删除原账号的草稿。新草稿在插件数据目录的 `maintenance-v2/`；当前任务材料、对话和 worktree 在 `task-sessions-v2/`。打开或恢复任务、复制推送命令之前会重新核对身份。唯一的插件 GitHub 写入是从最终预览明确确认的 Issue 创建。

社区收件箱、个人书签与验收、批次回顾与结算不是当前入口。旧版 `maintenance-v1/` 原始记录仍可在宿主机本地只读查看；没有查看旧记录的插件 UI，也不会按登录名迁入当前身份。详见[旧记录只读查看](docs/design.md#旧记录只读查看)。
