# TernMate

TernMate 是 [Tern](https://docs.stencil.so/tern/guides/blocks.html) 的 GitHub Issue / PR 工作台。在项目窗口里筛选任务，单击或按 `Enter`，即可在对应代码目录启动或恢复交互式 `omp` 会话，无需复制链接或补写提示。

## 安装

在 Tern 宿主机上准备 `tern`、`git`、`gh` 和 `omp`（可使用 Tern 随附的 `omp`）。使用 `gh auth status` 确认已登录；未登录时运行 `gh auth login`。读取 GitHub Actions 日志还要求 `gh api --help` 中列出 `--allow-escape-sequences`。

macOS 上 Tern 宿主的 `PATH` 可能与终端不同。TernMate 在宿主 `PATH` 之后查找 `/opt/homebrew/bin` 和 `/usr/local/bin` 中的 `gh`。若安装在其他目录，请将其加入 Tern 宿主的 `PATH`，而不只是 shell 的启动配置。

```sh
git clone https://github.com/gulanthys/TernMate.git
cd TernMate
tern plugin link .
tern plugin list
```

## 使用

1. 在 Tern 命令面板选择 **New TernMate**，工作台在当前 session 的来源面板右侧分屏打开。顶部显示任务仓库和本地路径。若有多个候选（如 fork 和上游），先选 `owner/repo`；之后可从 **仓库** 菜单切换目标或选 **本地 checkout…**。仓库发现使用来源面板的工作目录，不读取 `omp --cwd`。
2. **开发模式**保留 Issue / PR 列表和 **新建 Issue**。按 `Tab` 切换 Issue / PR，按 `/` 搜标题，或用 **快捷筛选** 和 **筛选**。筛选覆盖整个本地镜像，不限于当前页；`R` 主动同步。
3. **审核模式**只列开放、非草稿 PR，不限于请求我审查。可再按审查请求、线程或 CI 等条件筛选。没有新建 Issue 或复制推送命令入口。
4. 两个模式分别保留筛选和选中位置。按 `↑` / `↓` 选择，`←` / `→` 翻页，单击或按 `Enter` 打开对应的 omp tab；同一身份、checkout、模式和版本再次打开时，聚焦或恢复原会话。
5. **新建 Issue**支持本地草稿、查重、预览和明确确认；不支持的模板走 GitHub 原生入口。多窗口同时编辑时不会覆盖新版草稿，未保存的输入会留在编辑器供核对。仓库访问无法重新确认时，不读取原账号的草稿。发送使用经核对的同一账号凭据；仓库可见性变化后须重新预览。创建成功或首次关联网页原件后自动刷新列表，保留筛选和选中项。发送前校验失败可继续编辑；请求可能已发出但结果未知时只能核对回执，不能重发。模板解析和提交存储使用宿主的 `/usr/bin/ruby`。

开发模式的开放 Issue / PR 标签显示当前仓库的开放数量，不受列表筛选影响。要查看所有状态，使用 **快捷筛选 → 全部状态**。
Issue 和 PR 列表按编号从大到小排列，审核模式也一样。
点「刷新」或按 `R` 后，最新创建的 Issue 和 PR 会优先核对；扫描中再次刷新，会在本轮结束后再查一次。已核对的变化先显示，不等仓库历史全部扫完。未核对的旧行暂时保留；若扫描失败，重试也保留两种列表中已经核对的行，直到新证据更新它们。完整扫描成功后才显示准确总数。
只有最近一次同步成功、覆盖完整且没有待判定匹配项时，分页才显示「共 N 项」。同步中、失败或过期时仍可浏览已知行，分页显示「已找到 N 项」；仓库标签用「上次 N」标明旧的完整计数。

一条 PR 只显示一行；开放、草稿、已合并或关闭未合并的状态，与合并冲突、当前 head 的 CI 失败、未解决线程和请求我审查等信号并列，不互相覆盖。

Issue 和 PR 都直接按 OMP 的正常配置加载审批模式。TernMate 不修改全局配置、不逐个 PR 强制审批，也不自动批准工具调用；如果 OMP 的有效配置要求审批，仍会提示。

PR 会话禁止从 worktree 自动加载规则、上下文文件、技能、扩展和自定义系统提示，项目 MCP 也保持禁用。每次新建或恢复 PR 进程时，TernMate 通过所用 `omp config path` 找到当前用户配置目录，只把其中的 `RULES.md`（如有，须为普通文件而非符号链接）连同任务边界传入系统提示。全局规则不会授予远端写入权限，也不是命令级拦截器。

复用符合当前权限边界的运行中会话时只聚焦，不重启。升级前使用通用读取工具的审核会话不会被工作台聚焦或恢复；再次打开同一 PR 会新建受限审核会话，不改动旧面板或历史。旧进程的权限不会自动收紧，应正常退出。其他 PR 会话退出再恢复时使用新的全局规则。

首次启动失败时，若工作台能确认该进程已退出且未留下会话文件，可再次点击同一任务重试。不能确认时保留旧面板和记录，不创建替代会话。

旧版未绑定稳定身份的会话不会从工作台自动恢复。再次打开任务会在独立工作区另开会话；旧对话、旧 worktree 和原 checkout 的修改不会被迁移或删除。

Issue 行的「本机处理中」表示当前账号和 checkout 下，该 Issue 至少一个版本的 omp 面板仍开着，不是公开认领。已提交的 PR 若明确引用该 Issue，列表另显示如「PR #1183 开放」；合并不等于验收。未发现明确引用时不猜关联，也不自动创建 PR、打标签或关单。

首次选仓需在线核对仓库和账号并建立本机镜像。再次打开先读该身份的镜像；工作台开着时约每 5 分钟后台核对变化，失败退避并标明旧数据。完整核对成功即保存核对时间，即使列表内容没变。关闭工作台不运行常驻服务。镜像仅保存列表及维护所需的元数据，不包含任务正文、讨论或 CI 日志。

| 任务 | 打开后的行为 |
| --- | --- |
| Issue | 从所选 checkout 的已提交 `HEAD` 创建独立 worktree 和 `ternmate/issue-<编号>-<标识>` 本地分支。`omp` 在该目录只读分析正文、讨论和代码；明确要求修复后才修改。原 checkout 的未提交内容不带入。 |
| 开发模式 PR | 核对 PR head SHA 后在独立 worktree 打开，提供未解决审查线程及可读取的当前版本 CI 失败证据。可在本地修复和验证；不会自动推送、评论、解决线程、批准或合并。 |
| 审核模式 PR | 按目标分支名、base SHA 和 head SHA 固定审核版本。OMP 使用专用只读工具查看本次差异、任务材料并检索固定版本源码，不能借通用读取工具访问宿主文件或 URL。结论只在对话中给出；要修复请回开发模式。 |

普通打开按所选 checkout 的 HEAD（Issue）或实时核对的 PR 版本进入当前会话。审核即使 head 不变，改投目标分支或目标分支前移也使用不同审核版本。若准备或确认期间版本又变化，会重新提示，不替用户改选。此时可选择提示中的版本，也可点 **取消** 或按 `Esc` 返回原列表，不启动会话。打开新版本或关闭工作台不会关闭旧 omp 面板、删除对话或改动旧 worktree。**worktree 不是沙箱**：不要在带凭据的环境中运行不可信 PR 的脚本。

要手动推回 PR，先在独立 worktree 提交改动，再从对应 PR 的右键菜单选择 **复制推送命令**。TernMate 实时核对源仓库（含 fork）、源分支和远端 head；只有本地提交可快进时才复制指定提交和分支的命令。核对目标后自行执行；复制不会写 GitHub、设置默认远端或强推。

镜像、草稿和会话按 GitHub 主机、稳定仓库 ID 和稳定账号 ID 分开。检测到身份失效时，工作台关闭旧草稿面板并停止后续读写，不删除原账号的草稿。新草稿在插件数据目录的 `maintenance-v2/`；当前任务材料、对话和 worktree 在 `task-sessions-v2/`。打开或恢复任务、复制推送命令之前会重新核对身份。唯一的插件 GitHub 写入是从最终预览明确确认的 Issue 创建。

社区收件箱、个人书签与验收、批次回顾与结算不是当前入口。旧版 `maintenance-v1/` 原始记录仍可在宿主机本地只读查看；没有查看旧记录的插件 UI，也不会按登录名迁入当前身份。详见[旧记录只读查看](docs/design.md#旧记录只读查看)。
