# TernMate 项目维护方案研究

结论：以**需要作出的决定**组织工作台，而不是用一条从 Open 到 Closed 的流水线管理所有事项。批次用于划定范围，队列解释为什么需要行动，Issue／PR 保存原始证据，omp 帮助处理选中的任务。本文是产品建议，不是已实现能力。相关文档：[产品定位](requirements.md)、[FD 筛选研究](filter-research.md)。

## 开源场景复核：默认试点从批次改为贡献收件箱

**问题：** 不知道团队名单、不要求报告人安装 Tern、没有批次计划时，TernMate 是否仍能帮助维护者接住贡献？采用两种证据：读仓库的公开约定，看它希望人们怎么做；抽查实际 Issue／PR，看只依赖该约定会漏掉什么。规范是预期，不是当前某条 PR 已通过门槛的证据。

| 一手证据 | 对设计的修正 |
| --- | --- |
| FD 的 [Issue 配置](https://github.com/zerx-lab/FluxDown/blob/main/.github/ISSUE_TEMPLATE/config.yml) 禁止空白 Issue，并提供官网反馈、FAQ 和社区投票 | 「提交反馈」先展示渠道，再打开匹配表单。不要把提问、投票或私密问题一律公开发单；打开外部入口不等于已提交 |
| 对 FD 的 `pullRequests(last:50)` 抽样，不限状态：21 条跨仓，36 条没有 `closingIssuesReferences`。如 [#1139](https://github.com/zerx-lab/FluxDown/pull/1139) 是已合并的跨仓 PR，没有该类引用；[#1141](https://github.com/zerx-lab/FluxDown/pull/1141) 同为跨仓，作者关系却为 `COLLABORATOR` | PR 自身就是收件箱条目，不做 Issue 的必选子节点。不把“没有关闭引用”误称从未有讨论，不从 fork 推断是新人、非成员或拥有哪项权限；样本不代表全仓比例 |
| [FD 贡献指南](https://github.com/zerx-lab/FluxDown/blob/main/CONTRIBUTING.md) 指明新提交通常不触发机器人重审，文档 PR 需要维护者审查；标题 `【待合并】` 不等于 CI 已通过或已授权合并 | “等谁”至少区分作者、维护者、自动检查及未知。机器人回执、实质性机器审查、人工审查分别展示。若旧审查后已有新 head，显示两个提交及复审规则，不自动发表评论触发机器人 |
| [CPython 贡献指南](https://devguide.python.org/getting-started/quick-reference/) 建议多数变更先开 Issue，但 typo 等小改动例外；首次贡献需 CLA。[curl 贡献指南](https://curl.se/dev/contribute.html) 接收 PR 或邮件补丁，功能改动即使获批也可能要等 feature window | 支持直接 PR，但不对所有仓库推荐跳过讨论。贡献门槛和合并窗口展示仓库出处；未知时不给绿灯。不替用户签署协议，也不承诺同步外部邮件讨论 |

**产品分层。** 基础层只记录对象、证据来源及版本、下一动作与角色；角色未知就待核对。仓库层按已确认的规则解释标题、标签、渠道和审查门槛；规则只供导向，不作为命令运行。计划层由维护者主动启用：FD `830` 是盘点维度，不是社区贡献者的交付合同。合并后仍需按制品与渠道核实发布，反馈回到原件，不要求报告人必须签收。

**试点顺序。** 先让 FD 维护者在同一快照独立挑选“该我回应”“等贡献者”“等自动化”“无法判断”的条目，再对照工作台的命中原因。用无关闭引用的 fork PR、需要人工审查的文档 PR、旧审查对应新 head、没有批次的 Issue 作反例。误把自动回执算人工决定或漏掉独立 PR 时不推广；这层通过后再试下文的 830 回顾。尚未做维护者访谈，也未据样本验证响应时长或效率提升。

## 借鉴什么，不照搬什么

| 一手来源 | 实际做法 | TernMate 的取舍 |
| --- | --- | --- |
| [Kubernetes：Issue Triage Guidelines](https://www.kubernetes.dev/docs/guide/issue-triage/) | 分别判断事项类型、优先级与归属 SIG；缺信息时说明需要报告人补什么，并定期回看没有进展的事项 | 分开“谁负责这个领域”和“现在等谁行动”。小项目也能用维护者／报告人两个角色，不要求配置团队，不照搬其超时自动关闭政策 |
| [Rust 编译器团队：Prioritization](https://forge.rust-lang.org/compiler/prioritization.html) | `I-prioritize` 表示有人请求评估，不表示高优先级。结合复现、回归和影响决定等级，给出简短理由或讨论链接；潜在发布阻塞会被定期复核 | 把“待定优先级”“已有优先级”“明确阻塞发布”分开。不让模型因为标题写着“紧急”就判 P1，也不把所有 P1 自动算成发布阻塞 |
| [VS Code：Development Process](https://github.com/microsoft/vscode/wiki/Development-Process)、[Endgame testing and verification](https://github.com/microsoft/vscode/wiki/Endgame-testing-and-verification) | 迭代计划定义范围；Plan Item 事先列完成条件；收尾阶段验证修复与功能，未完成项可延期或退回积压池 | 借用“本批范围＋验收条件＋逐项结算”，而不是固定月度发版或复制整张检查表。批次标记不是发布时间，延期不是完成 |

## 建议的日常操作

| 打开哪份清单 | 维护者要作什么决定 | 本轮何时结束 |
| --- | --- | --- |
| 新到与待分诊 | 属于本项目吗？可复现吗？接收、请补信息、指向重复项，还是不采纳？ | 有明确去向；缺信息时写清缺什么、等谁。没有分诊信号只列为候选，不断言没人处理 |
| 本批待决策 | 哪些方案要批准，哪些事项值得插队，哪些应顺延？ | 每个待决项有决定或明确的下一步；未排期可以是合理结果，不强迫填日期 |
| 进行中与卡点 | 卡在产品决定、作者修改、评审、CI，还是等报告人复测？ | 每项显示原因、下一行动角色和来源；一项多因只列一次。若角色不明，标“待确认”，不猜人名 |
| 待验收与批次收尾 | 原问题在目标平台／版本解决了吗？这一批哪些可交付、延期、撤回或仍待决定？ | 对照原接受条件和实际验证版本给结论。已合并、已验证、已发布分别记录；重复项或咨询可以用指向原问题或已答复作为结论，不必有 PR |

日常先看等自己决定或阻塞本批的事项；定期回看等待太久的事项；批次结束时复核验收与延期。等待时长从**进入该等待状态的证据**算起，只有 `updatedAt` 时只能显示“多久未更新”。例行回顾是提醒，不是关闭、改标签或催办的授权。

## 用 FD 检查这个方案会不会误导人

- **同样的标题，不一定都要行动。** [#329](https://github.com/zerx-lab/FluxDown/issues/329) 与 [#277](https://github.com/zerx-lab/FluxDown/issues/277) 都写了 `【830】【待批准方案】`，都有 `roost:proposal`；本次查询前者开放、后者已关闭。“830 待我方批准”应列前者，后者在批次历史可查，但不能因遗留标记重回待办，也不能因关闭就称为已交付。决定由维护者作出，打开 omp 不等于批准。
- **一个维护事项可以横跨 Issue 和 PR。** [#1180](https://github.com/zerx-lab/FluxDown/issues/1180) 标了 `roost:pr`；[PR #1183](https://github.com/zerx-lab/FluxDown/pull/1183) 的 `closingIssuesReferences` 明确指向 #1180，审查决定为 `CHANGES_REQUESTED`。在事项视图显示“已有实现，审查要求修改”，点击卡点进入 PR；不把两条记录算成两项需求。该 Issue 没有 `【批次】`，不能因有 PR 就推断它属于 830。反过来，只有 `roost:pr` 却找不到可核对的 PR 时，显示“标记有关联，链接待确认”。
- **审查问题未必是行评论。** [#1211](https://github.com/zerx-lab/FluxDown/pull/1211) 的采集记录中，当前提交有请求修改的整体 review，没有未解决线程且 CI 成功。它仍属审查卡点，不是“可验收”。以上均为观测快照，不是永久状态。

## 跨仓库采用方式

最小单位不是一张待填写的新卡片，而是一个带依据的判断：**事项、所处批次、下一动作、谁来做、为何这么判断、怎样算完成**。只有当前决策需要的字段才展示；优先复用已有记录，避免维护者在 GitHub 和 Tern 各维护一份台账。

- **无需配置即可使用：** 原生 open/closed、PR 关联、审查决定和与当前提交关联的 CI 直接读取。一个 PR 可以关联多个 Issue，一个 Issue 也可以有多个 PR；保持各自身份，不把相关项全部折叠成一个任务。
- **让仓库解释自己的约定：** FD 可把标题前缀映射为批次和阶段；另一个项目可用 milestone、标签或有权限读取的 Projects 字段。先展示命中样例，再由维护者确认含义。标题和标签结论冲突时并列出处、提示复核，不静默择一；请求失败不等于没有事项。
- **区分事实、建议与决定：** GitHub 状态是事实；“建议顺延”只是建议；维护者确认的决定要有出处。选队列或进入 omp 均不回写 GitHub。没有已发布版本或验收记录，就明确写“发布未知”或“待验证”。

## 先做哪一项验证

建议先试 **FD 的一轮 830 批次回顾**，而非先开发通用流程编辑器。维护者手工列一份对照清单，注明待批准事项、已有关联修复的事项和结案理由；在同一采集快照下与只读工作台逐项比对。至少检查：#329 入待批准、#277 只入历史；另用无批次的 #1180/#1183 验证事项关联，不混入 830。再换用 milestone 的仓库，验证无需改写标题也能做同样的批次回顾。

评价标准：是否漏掉需要决定的条目；是否把等待别人或已经关闭的条目误报为待办；维护者能否直接看出处并决定下一步；批次回顾是否比手工逐条开页更省操作。没有对照结果前，不宣称提高了维护效率。
