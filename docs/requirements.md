# TernMate 产品需求

本文定义当前开发／审核模式的用户契约和回归场景的预期；安装和历史验收证据见[技术设计](design.md)。

## 目标与范围

当前工作台提供选仓、Issue／PR 镜像和筛选、开发／审核 omp 会话，以及开发模式的「新建 Issue」。审核模式只列开放、非草稿 PR，不限于请求我审查；没有新建 Issue 或复制推送命令入口。两个模式分别保存筛选和选中位置。

### 维护流程（产品方向，不是当前入口）

社区收件箱、个人书签与验收、批次回顾与结算不在当前工作台中；下表是维护决策的设计背景。已有本机记录的只读查看方式见[技术设计](design.md#旧记录只读查看)。

| 维护决策 | 需要记录什么 | 何时移出当前队列 |
| --- | --- | --- |
| 分诊：这件事值得做吗？ | 问题、影响范围、是否缺少复现信息、下一步由谁行动 | 明确接受、暂缓、不采纳或等待谁补充；不把无人指派当作无人处理 |
| 排期：这批准备做什么？ | 处理批次、优先级与纳入理由；允许保留尚未排期的事项 | 选入批次，或明确移出；报告版本不等于目标批次 |
| 执行：目前卡在哪里？ | Issue 与相关 PR、阻塞原因、下一步动作；不要求每条 Issue 都有 PR | 有可供验证的修复、答复或决策，不因创建 PR 就标记完成 |
| 验收：原问题解决了吗？ | 原始接受条件与验证证据；若涉及发布，区分本地验证、已合并和已发布 | 按该事项的完成条件确认；缺证据则保留待验证 |

**通用的是维护问题，不是标签词典。** 例如 FD 的 `【830】【待批准方案】` 表示一条事项既属于 `830` 批次，又在等待方案批准。维护者应能直接回答“830 批次还有哪些方案等我决定”，而不用在两个字段之间二选一。其他仓库可以用 milestone 表达批次、用标签表达阶段，不必改成 FD 的标题格式。字段映射及样本见[筛选研究](filter-research.md)。查看队列只读；决定下一步不等于授权插件回写 GitHub。

## 从反馈到 Issue

开发模式的 Issue 列表提供独立的「新建 Issue」入口，不把“打开已有 Issue”变成写操作。按目标仓库的模板和联系渠道报告，不自动上传会话、文件或日志。

1. 确认提交到哪个仓库、以哪个账号提交、谁能看到内容。选择目标仓库提供的 Bug／功能建议模板；仓库要求走支持或私密渠道时转交对应入口，不绕过规则创建公开 Issue。
2. 在本机保存草稿、查看相似的开放及已关闭事项。报告 Bug 时填写复现、实际／期望行为、受影响环境；建议类说明场景和期望结果。报告人填的是**遇到问题的版本**，无须决定优先级、维护者或 `【830】` 处理批次。
3. 预览最终目标、标题、正文及随模板提交的元数据；显式确认才创建一个 Issue。成功后给出可核对的 `owner/repo#编号` 和链接，可直接打开 omp 或返回原列表。取消、失败、结果未知均不得丢草稿或静默重发。
4. 新建不等于接受需求。维护者可在原 Issue 处理分诊，报告人可通过原 Issue 跟踪、补充和复测。最终回复应能说明如何结案，若已修复则给出适用版本或注明尚未发布。插件不代替维护者发送回复。

## 从筛选到继续工作

1. 从项目目录打开工作台。若 fork 和上游都可作为目标，选择一次；面板持续显示 `owner/repo`。无法关联本地仓库时提示选择，不在任意目录启动分析。
2. 切换 Issue / PR，选择快捷筛选或组合条件。显示生效条件、逐项移除和清空入口。快捷入口不是额外限制：用户可以查看不属于自己的开放项。
3. 单击一行或按 Enter 直接进入交互式 omp。`↑` / `↓` 移动选择，`←` / `→` 翻页。启动期间显示进度；重复点击不得创建第二个会话。
4. 返回列表后保留原仓库、筛选和位置。刷新后优先保留选中条目；若已不匹配，选相邻项。再次打开同一身份、模式、checkout 和版本的任务，应聚焦或恢复原会话。

## 列表与检索

| 类型 | 快捷入口 | 可组合条件 |
| --- | --- | --- |
| Issue | 全部开放、分配给我、我创建的 | 开放／已关闭、负责人、作者、标签、标题关键词、精确编号 |
| PR | 全部开放、我提交的、请求我审查、有未解决线程、CI 失败、我的待处理 PR | 开放／已合并／关闭未合并、草稿、作者、目标分支、标签、标题关键词、精确编号、审查与 CI 状态 |

不同条件取交集；“我的待处理 PR”包括**我提交的开放 PR，且存在合并冲突、未解决线程或当前 head 的 CI 失败**。一条 PR 只显示一行，生命周期状态（开放、草稿、已合并、关闭未合并）独立于合并冲突、CI 失败、未解决线程与请求我审查等并列信号。尚未判定的可合并性不视为无冲突；收到审查请求不等于存在未解决意见。筛选面向整个目标仓库；加载中、部分结果、确认无匹配、无权限必须可区分。

镜像、草稿和任务记录按 GitHub 主机、稳定仓库 ID 与稳定登录账号 ID 隔离；换账号不得沿用原身份的会话或草稿，不按登录名自动迁移旧记录。打开或恢复任务、复制推送命令仍需在线校验仓库和账号。浏览不触发网络轮询；后台核对失败时保留可用的已知事实并标明局限。成功完成覆盖核对即持久化新鲜度，即使列表内容没变化；失败或未完成的核对不算成功。Issue 的本机处理提示、已提交 PR 的明确关联、远端合并、验收通过是不同事实，均不因浏览而回写到 GitHub。

## 点击后的任务契约

**Issue：先分析。** 在工作台所属 Tern session 的独立 tab 中启动或恢复 omp。每个 Issue 从所选 checkout 的已提交 `HEAD` 创建自己的本地分支和 worktree；不带入原 checkout 的未提交修改。首次以中文发出分析请求，保留标题、正文、讨论和来源链接的原文。首轮用中文区分用户报告、代码证据和待验证假设，并给出下一步。点击本身不授权修改；用户可在同一会话要求修复。

**开发 PR：处理已有问题。** 在已核对 head 的独立工作区内审查未解决线程、定位当前版本 CI 失败，并按用户要求本地修复和针对性验证。报告区分代码失败、基础设施问题与证据不足；本地通过不等于远端通过。不得因打开 PR 自动推送、评论、关闭线程、批准或合并。复制推送命令需核对当前 head、源仓库和源分支（可来自 fork）；不执行命令。

**审核 PR：只读审阅固定差异。** 审核与开发的 worktree、进程和会话记录分开。审核版本由目标分支名、base SHA 和 head SHA 共同标识，差异从固定 base 与 head 的共同祖先起算。审核工具只能读取本次任务材料、固定差异和对应版本的源码，不访问宿主其他路径或网络地址。结论只在 omp 对话中给出；恢复不改写已有材料。

**版本选择和保留。** 普通打开按所选 checkout 的已提交 HEAD（Issue）或实时核对的 PR 版本进入当前会话。若 PR 在准备或确认期间再变化，先重新提示；确认只打开所选的精确版本。取消提示不启动会话、不改变列表选择。打开新版本不会关闭旧面板、删除会话文件或改动旧工作区。

## 当前契约的回归场景（预期，不是验收结果）

| 场景 | 可观察结果 |
| --- | --- |
| fork 中选择上游，点击分配给我的 Issue | omp 打开的编号和链接属于上游，结合代码给出分析，文件未被改动 |
| 并行处理同仓库的两个 Issue | 分支和 worktree 不同；同一文件的改动不互相影响；重开同一 Issue 仍使用原任务分支，原 checkout 不变 |
| 唯一匹配项不在第一页 | 能找到该项；扫描结束前不显示“无匹配” |
| PR 同时有未解决线程和当前失败检查，或已合并 PR 仍有信号 | 每条 PR 只出现一次，显示独立的生命周期状态和所有已知并列信号；会话仅引用可关联该版本的证据 |
| 上次 CI 失败，新 head 检查尚在运行 | 不标为当前失败；日志不可读时说明原因而不推断根因 |
| 连点同一 PR，关闭 omp 后再次打开 | 不重复创建；恢复原任务上下文，不误开同仓库的其他对话 |
| 同一 head，目标分支改名／改投，或 base SHA 前移 | 原审核差异不充当当前版本；选择当前版本后使用新目标分支与固定 base/head 计算差异 |
| 提示打开版本 B 后 PR 又变为 C | 确认 B 不会启动 C；提示新版本以便重新选择，首次打开也如此 |
| 旧 omp 仍在运行，且 worktree 有本地修改或提交 | 打开新版本后，旧面板、对话文件、工作区及改动仍保留 |
| 草稿打开时在同一 checkout 换账号；同一账号登录名更新 | 检测到换号后关闭旧草稿并拒绝旧面板的后续操作；新账号不能读取旧数据。稳定 ID 不变仍归同一分区，旧登录名分区不自动并入 |
| 无行变化但同步成功，关闭再打开 | 读取最近一次成功核对时间，不因行没变从旧时间重新计时 |
| 离线、未登录或被限流 | 给出原因与可行的下一步；错误不伪装成空列表或 CI 通过 |

## 范围边界

当前范围是选仓、筛选、任务会话、只读审核、本地分析／修复和明确确认的 Issue 创建。社区收件箱、个人验收、批次管理、列表内批量管理、跨仓库通知和 Projects 看板不属于当前入口；除明确确认的 Issue 创建外，插件不写 GitHub。
