# TernMate 产品需求

状态：首版已实现。本文定义用户可见行为；安装步骤和验收范围见[设计方案](design.md)。

## 目标与范围

TernMate 的目标是定义一套可复用的项目维护方案，让维护者能决定：这一批准备做什么、哪些事项卡住了、下一步由谁处理、凭什么认定已完成。筛选是查看维护队列的手段；Tern 提供工作台，omp 承接具体任务。一次点击打开正确上下文是交互要求，不是项目管理的最终目标。

### 维护流程（产品方向，不等同于首版已实现）

| 维护决策 | 需要记录什么 | 何时移出当前队列 |
| --- | --- | --- |
| 分诊：这件事值得做吗？ | 问题、影响范围、是否缺少复现信息、下一步由谁行动 | 明确接受、暂缓、不采纳或等待谁补充；不把无人指派当作无人处理 |
| 排期：这批准备做什么？ | 处理批次、优先级与纳入理由；允许保留尚未排期的事项 | 选入批次，或明确移出；报告版本不等于目标批次 |
| 执行：目前卡在哪里？ | Issue 与相关 PR、阻塞原因、下一步动作；不要求每条 Issue 都有 PR | 有可供验证的修复、答复或决策，不因创建 PR 就标记完成 |
| 验收：原问题解决了吗？ | 原始接受条件与验证证据；若涉及发布，区分本地验证、已合并和已发布 | 按该事项的完成条件确认；缺证据则保留待验证 |

**通用的是维护问题，不是标签词典。** 例如 FD 的 `【830】【待批准方案】` 表示一条事项既属于 `830` 批次，又在等待方案批准。维护者应能直接回答“830 批次还有哪些方案等我决定”，而不用在两个字段之间二选一。其他仓库可以用 milestone 表达批次、用标签表达阶段，不必改成 FD 的标题格式。字段映射及样本见[筛选研究](filter-research.md)。查看队列只读；决定下一步不等于授权插件回写 GitHub。

## 从反馈到 Issue（拟新增）

Issue 列表提供独立的「新建 Issue」入口，不把“打开已有 Issue”变成写操作。报告人可以从空白开始，也可以从验收失败、发布后回归或已有任务进入；只预填已选的来源链接，不自动上传会话、文件或日志。

1. 确认提交到哪个仓库、以哪个账号提交、谁能看到内容。选择目标仓库提供的 Bug／功能建议模板；仓库要求走支持或私密渠道时转交对应入口，不绕过规则创建公开 Issue。
2. 在本机保存草稿、查看相似的开放及已关闭事项。报告 Bug 时填写复现、实际／期望行为、受影响环境；建议类说明场景和期望结果。报告人填的是**遇到问题的版本**，无须决定优先级、维护者或 `【830】` 处理批次。
3. 预览最终目标、标题、正文及随模板提交的元数据；显式确认才创建一个 Issue。成功后给出可核对的 `owner/repo#编号` 和链接，可直接打开 omp 或返回原列表。取消、失败、结果未知均不得丢草稿或静默重发。
4. 新建不等于接受需求。维护者从待分诊入口接手，需要补充则说明“缺什么、等谁”。报告人可通过原 Issue 跟踪、补充和复测；最终回复应能说明如何结案，若已修复则给出适用版本或注明尚未发布。插件不代替维护者发送回复。

## 从筛选到继续工作

1. 从项目目录打开工作台。若 fork 和上游都可作为目标，选择一次；面板持续显示 `owner/repo`。无法关联本地仓库时提示选择，不在任意目录启动分析。
2. 切换 Issue / PR，选择快捷筛选或组合条件。显示生效条件、逐项移除和清空入口。快捷入口不是额外限制：用户可以查看不属于自己的开放项。
3. 单击一行或按 Enter 直接进入交互式 omp。方向键只移动选择。启动期间显示进度；重复点击不得创建第二个会话。
4. 返回列表后保留原仓库、筛选和位置。刷新后优先保留选中条目；若已不匹配，选相邻项。再次打开同一任务，应聚焦或恢复原会话。

## 列表与检索

| 类型 | 快捷入口 | 可组合条件 |
| --- | --- | --- |
| Issue | 全部开放、分配给我、我创建的 | 开放／已关闭、负责人、作者、标签、标题关键词、精确编号 |
| PR | 全部开放、我提交的、请求我审查、有未解决线程、CI 失败、我的待处理 PR | 开放／已合并／关闭未合并、草稿、作者、目标分支、标签、标题关键词、精确编号、审查与 CI 状态 |

不同条件取交集；“我的待处理 PR”包括**我提交的开放 PR，且存在合并冲突、未解决线程或当前版本 CI 失败**。命中多个原因仍只显示一行，并分别标明。GitHub 尚未判定可合并性时显示「可合并性未知」，不视为无冲突。收到审查请求不等于存在未解决意见。筛选面向整个目标仓库；加载中、部分结果、确认无匹配、无权限必须可区分。

工作台在本机保存按仓库和登录身份隔离的 Issue／PR 镜像。浏览不驱动网络轮询；后台核对变化，失败时保留已知事实并标明局限。Issue 的本机处理提示、已提交 PR 的明确关联、远端合并、验收通过是不同事实，均不因浏览而回写到 GitHub。

## 点击后的任务契约

**Issue：先分析。** 在工作台所属 Tern session 的独立 tab 中启动或恢复 omp。首次以中文发出分析请求，交给 omp 的标题、正文、讨论和来源链接保留原文。首轮用中文区分用户报告、可定位的代码证据和待验证假设，并给出下一步。点击本身不授权修改；用户可在同一会话要求修复。

**PR：处理已有问题。** 在工作台所属 Tern session 的独立 tab 中启动或恢复 omp，首次发出中文任务请求。omp 在对应 PR head 的独立工作区中，针对未解决线程核对当前代码，区分需修改、已修未关闭、需要作者判断。针对 CI 定位失败检查、job、step 及可读日志；区分代码失败、基础设施问题与证据不足。可执行本地修改和针对性验证。报告应逐项说明处理结果；本地通过不等于远端通过。不得因打开 PR 自动推送、发评论、关闭线程、批准或合并。

首次生成的 PR 任务材料另附 GitHub 合并状态及当时的 head、目标分支和 base SHA，和审查、CI 证据分开。恢复旧会话不改写已有材料。

## 首版验收场景

| 场景 | 可观察结果 |
| --- | --- |
| fork 中选择上游，点击分配给我的 Issue | omp 打开的编号和链接属于上游，结合代码给出分析，文件未被改动 |
| 唯一匹配项不在第一页 | 能找到该项；扫描结束前不显示“无匹配” |
| PR 同时有未解决线程和失败检查 | 待处理列表只出现一次；会话拿到两类证据，在正确提交上修复并验证，原工作区未变 |
| 上次 CI 失败，新 head 检查尚在运行 | 不标为当前失败；日志不可读时说明原因而不推断根因 |
| 连点同一 PR，关闭 omp 后再次打开 | 不重复创建；恢复原任务上下文，不误开同仓库的其他对话 |
| 本地修复未提交，远端 PR 有新提交 | 明示版本差异；不丢弃修改、不静默切换提交 |
| 离线、未登录或被限流 | 给出原因与可行的下一步；错误不伪装成空列表或 CI 通过 |

## 范围边界

首版优先保证选仓、筛选、任务会话和本地分析／修复。列表内批量管理、跨仓库通知、Projects 看板和自动回写 GitHub 不作为首版交付条件。
