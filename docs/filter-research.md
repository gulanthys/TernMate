# 筛选设计研究：从 FluxDown 到任意仓库

这是筛选器的历史研究建议，不是当前筛选谓词或操作说明。目标：在打开 omp 前回答“下一条该处理什么、为什么是它”。当前开发／审核模式的实际范围与筛选契约见[产品需求](requirements.md#列表与检索)；标题批次和维护队列方案不代表当前入口。

## 样本与口径

以 [FluxDown Issues](https://github.com/zerx-lab/FluxDown/issues)、[PR](https://github.com/zerx-lab/FluxDown/pulls)、[仓库标签](https://github.com/zerx-lab/FluxDown/labels)为主。只读查询：REST 分页遍历开放条目、剔除 `pull_request` 后按编号去重；GraphQL 遍历开放 PR，分别读取审查决定、线程、最后提交的检查汇总。另取最近更新的 50 个关闭 PR 作对照。以下为本次采集快照，不是实时徽标，多标签计数不可相加。

| FluxDown 观察 | 设计含义 |
| --- | --- |
| 172 个开放 Issue，0 个有负责人；119 个 `enhancement`，42 个 `bug` | 默认“全部开放”，突出类型；保留“分配给我”，但不让首次打开落在空队列 |
| 132 个有 `triaged`；31 个 `roost:maintainer`、22 个 `roost:proposal`、15 个 `roost:waiting` | “尚无分诊标记”与“需要维护者处理”是不同队列；等待反馈不等于低优先级 |
| `prio:p1/p2/p3` 分别为 2/26/10 个；`platform:windows/linux/macos` 分别为 41/5/2 个 | 优先级、平台有实际区分度，但没有这些标签不能解释为低优先级或不涉及平台 |
| 4 个开放 PR 都是非草稿、目标 `main`、审查决定为 `CHANGES_REQUESTED`；全部没有未解决线程，也无待答复的审查请求 | “请求我审查”“被要求修改”“有未解决线程”必须是三个独立谓词，不能用其一代理另两个 |
| PR head 检查汇总为 1 个失败、3 个成功；最近更新的 50 个关闭 PR 在查询时均无标签 | PR 应以 GitHub 原生审查与检查字段为主；不能依赖 PR 标签、标题前缀或仓库最近一次 Actions 运行 |

## FluxDown 推荐界面

| 入口 | 默认与快捷项 | 展开后再选 |
| --- | --- | --- |
| Issue | 默认“全部开放”，首屏可选**标题版本批次**、分诊阶段和类型；保留“待维护者”“待补充”“待评估提案”的标签快捷项 | 客户端／平台、功能域、优先级、模板中的报告版本、负责人、原始标签等；标题搜索和 `#编号` 独立于版本选择 |
| PR | 默认“全部开放”，快捷项为“需处理审查意见”“CI 失败”“请求我审查”“我的待处理”。每行同时显示审查与 CI，允许多个命中原因 | 精确审查决定、是否有未解决线程、CI 状态、草稿、目标分支、作者／负责人、合并／关闭状态、原始标签 |

“待补充”按仓库定义的工作流标签匹配；`needs-info` 仍可单选，不假定两者同义。“无分诊标记”只是 `NOT label:triaged`，不是断言没人看过。`platform:*` 应标作**平台标签**；[Bug 模板](https://github.com/zerx-lab/FluxDown/blob/main/.github/ISSUE_TEMPLATE/bug_report.yml)另有 OS 和协议，[功能模板](https://github.com/zerx-lab/FluxDown/blob/main/.github/ISSUE_TEMPLATE/feature_request.yml)有 Scope。本次仅 16 个开放 Issue 有协议字段标题，不建议把协议放在首页。若提供高级表单过滤，只解析可识别模板的问题及选项，保留“未提供”，不把自由文本出现 `Windows` 当成操作系统结论。

**建议调整原需求中的 PR 队列：**

- `需处理审查意见 = 审查决定为 CHANGES_REQUESTED OR 存在未解决线程`。独立保留“仅未解决线程”。`我的待处理 = 开放 AND 作者是我 AND (需处理审查意见 OR 当前版本 CI 失败)`。按 PR 身份去重，展示具体原因。
- [#1211](https://github.com/zerx-lab/FluxDown/pull/1211) 的请求修改写在当前提交的整体 review 正文里，CI 成功且没有未解决线程。原谓词会漏掉它；点开时 omp 必须拿到 review 正文，不只是行评论。
- [#1176](https://github.com/zerx-lab/FluxDown/pull/1176) 则同时命中请求修改和 CI 失败，但请求修改针对旧提交。列表保留 GitHub 的审查决定，详情标注 review 对应的提交，由 omp 核对当前代码；不要声称旧意见仍可复现。

## FD 的标题不是纯文本：版本批次、阶段、范围

补查全部状态的 Issue：REST 遍历得到 979 个 Issue，均未挂 milestone；GraphQL 分页读取标题和状态，有 198 个标题的连续前缀包含独立的数字 `【…】` 标记。下表是采集快照，不能当作配置枚举。

| 标题批次 | 开放 | 已关闭 |
| --- | ---: | ---: |
| `730` | 4 | 10 |
| `830` | 41 | 16 |
| `930` | 16 | 2 |
| `1030` | 67 | 18 |
| `1130` | 18 | 6 |

- **首屏放“版本批次（标题）”**：默认全部，可多选，也可选“未标注”。按编号值自然排序但保留原文，不推算日期、SemVer、发布顺序或“当前版本”。例如选 `830` 和 `930` 再选开放，是两个批次的并集与开放状态的交集，而非全文搜索 `830 OR 930`。
- **一个标题可以贡献多个维度。** [#277](https://github.com/zerx-lab/FluxDown/issues/277) 的 `【830】【待批准方案】【通用】【分类】【文件管理】` 分别提供批次、阶段和范围。[#1027](https://github.com/zerx-lab/FluxDown/issues/1027) 可同时匹配 `服务端`、`Web`、`Mac`。解析开头连续、闭合的 `【…】`，数字 token 整项匹配；其他 token 按仓库映射分组，不按第几个括号猜含义。未识别的保留为“其他标题标记”。原题不改写。
- **区分三个版本问题。** “属于哪个处理批次”读标题；“用户在哪个产品版本遇到问题”读 Bug 表单的 Version（如 [#1212](https://github.com/zerx-lab/FluxDown/issues/1212) 的 `v0.6.8`）；“计划在哪个里程碑交付”读 GitHub milestone。分别显示来源，可组合，缺失时不拿另一字段补。扩展版本也不默认等于桌面版本。
- **精确性与刷新。** 未标注指已读取的标题没有匹配批次；未取到的页不是未标注。`#830`、正文引用、日志毫秒 `.930` 和标题中间的裸数字都不算。改标题后按新标题替换派生字段，不保留旧批次；保存筛选时保存所选批次而非当时的条目编号。
- **推广到其他仓库。** 复用“维度、来源、提取规则、原值”模型，不复用 FD 的词典。优先识别仓库已有的结构化来源（milestone、标签、可访问的 Projects 字段）；对重复标题模式，展示样例与覆盖率供维护者确认其语义后启用。映射按仓库保存；没有可靠来源时不显示该维度。标题规则在插件侧处理候选页，不要求用户修改 GitHub 标题或补标签。

## 如何通用化

对照 [cli/cli Issues](https://github.com/cli/cli/issues) 最近更新的 50 个开放项，实际出现的是 `priority-3`（13 个）、`priority-2`（6 个）和 `gh-pr`（15 个），不是 FluxDown 的 `prio:*`。其[最近更新的 20 个开放 PR](https://github.com/cli/cli/pulls) 有 12 个草稿、8 种目标分支。此处是定额样本，不能据此推断全仓比例；它足以说明为什么不应硬编码 `main`，也不应给所有仓库隐藏草稿筛选。

1. **通用层固定语义。** 状态、身份、原始标签、标题与编号来自 GitHub。PR 的审查决定、审查请求、线程、版本相关 CI 分别取值。“我”取目标主机上的登录身份。支持任意原始标签，仓库没有分诊或平台约定也可使用。
2. **仓库层只做发现和映射。** 读取真实标签名称、描述、分支及其使用情况；按命名族建议分组，例如 `prio:*` 或 `priority-*`。显示原始名称、可编辑／取消推荐；不要推断两个仓库的 P1 含义相同。标签计数只影响推荐顺序，不决定是否允许筛选。工作流标签只用于筛选，不触发 bot、改标签或写回 GitHub。
3. **个性化层保存谓词，不保存结果。** 按主机、仓库、Issue／PR 分开保存快捷项和条件。不同维度 AND，同一枚举多选 OR；多个原始标签明确提供“任一／全部”。展开快捷项即可见其条件；标签被删除时提示失效，不静默移除条件扩大结果。
4. **保证完整性。** 先按便宜的原生字段缩小候选，再按需补齐线程和检查。未取全的页数或未知子条件不算否定：例如审查或 CI 任一已确认满足即可入队；其他条件为否而 CI 不可读时标为未确定。计数注明范围，不把首屏计数当全库计数；本地验证不改变远端 CI 筛选值。

**验收建议：** 固定样本覆盖“请求修改但无线程且 CI 成功”“旧 review + 新提交”“同一 PR 双命中”“协议字段缺失”“无标签体系仓库”。真实仓库只做只读抽查，不把随时变化的线上数量写成自动测试断言。
