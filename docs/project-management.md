# TernMate 项目管理方案：从路线图到发布后复盘

**适用范围：** 用 GitHub 维护、持续交付的软件项目。目标是让维护者知道为什么投入、谁作决定、什么阻塞交付、如何确认用户已经受益。可以只靠现有 Issue、PR 和发布记录执行本方案；TernMate 是读取证据、组织队列与进入 omp 的工作台，不是另一套必须同步的工单系统。本文是建议的运行手册，不代表插件已实现全部视图，也不替代组织的财务或人事制度。

## 开源默认：先支持贡献，再按需启用承诺管理

不按仓库公开／私有切换两套流程。一个公开仓库可以有固定发布团队，也可以主要依靠偶发贡献。默认用社区收件箱组织反馈和贡献；只有维护者明确采用批次计划，才在其上叠加承诺管理。

| 社区入口 | 维护者要判断什么 | TernMate 不应做什么 |
| --- | --- | --- |
| 用户报告问题 | 是否能复现、是否属于本项目、缺哪项信息；咨询或敏感问题引导到项目指定渠道 | 不要求报告人懂优先级、认领修复或先建本地 checkout 才能向 GitHub 报告 |
| 社区提出建议 | 区分“欢迎有人贡献”“需先讨论方案”“核心成员已承诺”和“目前不做”；重大设计按仓库贡献指南走提案 | 不以点赞数定优先级，不把接受方向或 `help wanted` 当交付承诺 |
| 外部贡献者直接开 PR | 即使没有 Issue、负责人或批次，也进入待审查队列。先判断改动是否合适，再看缺评审、等作者修改或 CI 受阻 | 不强制补开 Issue；若项目指南要求先讨论，只提示出处。fork PR 不在带凭据宿主自动运行脚本 |
| 贡献暂停或交接 | 显示最近的明确请求和下一行动角色；维护者可邀请接手或继续等待，并在原讨论确认交接 | 不因沉默判定放弃、逾期或验收通过，不自动催办、撤销认领、关单或给个人排名 |

首页建议让维护者先处理「待首次回应」「待维护者决定／评审」「等报告人／贡献者」，让贡献者能找到「欢迎贡献」「我提交的反馈／PR」。区分“机器人已回执”和“维护者已回应”；身份或讨论记录不可核对时标未知。是否已发布按版本证据向原讨论反馈，不要求偶发用户必须回来签收。

验收例：FD 的 `【830】【待批准方案】` 可进入维护者决策队列，不自动进入承诺清单；一个未标批次、未关联 Issue 的社区 PR 同样可从收件箱打开。关闭批次功能，两条路径都应保留。

### 四个不依赖“理想参与者”的处理规则

收件箱分别保存或引用五种事实：GitHub 开关状态、问题是否可判断、接手信号、实现证据、验收结论。它们不是同一个状态字段。以下是拟采用的队列规则，不是要求所有贡献者填写的新表单。

1. **报告不完整、联系不上。** 提交人可能只是官网反馈的转发账号。先用已有材料判断，列出一个最有区分度的缺口；只有已通过合适渠道问过才显示“已请求补充”。报告人不可达时，转到“可独立调查”（同类报告、公开样例、可复现实验），或“缺证暂存”（原因、可恢复调查的条件）。新证据到来可重新分诊；不把无回复解释为问题不存在，不要求寻找私人联系方式。
2. **无指派，允许自取也允许不登记。** 信号按来源显示：无可见接手记录、本人本机标记“我在看”、公开认领、已有关联 PR。本机标记只用于继续自己的工作；打开 omp 不是认领，PR 作者也不是整条 Issue 的负责人。开始前展示已有 PR 和公开认领，减少重复劳动；查不到只能说“未见接手信号”，不锁单、不阻止另一位开发者参与。
3. **已处理但仍开放。** 有修复声明或合并证据时优先进“待验证”而非“待开发”；按原条件验证通过后退出修复队列，在“已验证／仍开放”视图可查，默认不提醒关单。记录型、讨论型 Issue 可长期开放，子问题解决不等于整条已验收。后续有效反例重回调查，保留前次验证范围和版本。关闭动作由维护者按仓库习惯决定。
4. **验收人不必是原报告人。** 可由具备目标环境的维护者、贡献者或报告人验证。最小证据：原症状／接受条件、环境与构建或提交、复现输入及操作、预期与实际结果、验证者与证据出处。缺陷优先做修复前失败／修复后通过的同条件对照；无法跑旧版时注明限制。功能建议按获认可的使用场景验收，不能把“全量 CI 绿”当成某一用户场景已验证。给出“指定范围通过／失败／验证受限”结论；本地自测、独立复测和用户反馈注明来源。无人具备原环境时保持受限，不能自动升级为通过。

**验收示例（假设，非 FD 线上结论）：** Windows 上暂停 BT 文件选择后重启，期望选项仍保留。用同一输入和配置分别运行已知受影响构建和候选构建，实际重启应用并核对持久化结果；记录构建、系统和结果。旧版丢失、新版保留，才可说“该 Windows 场景通过”。只有 Linux 的单元测试通过则记录局部证据，Windows 仍待验证；即使 Issue 仍开放，也不用重新派开发任务。

## 落地约定：从一次只读批次回顾开始

**第一项交付不是计划编辑器，而是可与维护者手工清单核对的批次回顾。** 目前已有选仓、Issue／PR 列表、筛选和 omp 会话入口（见[现有实现](design.md)）；下面的批次映射、开批基线和结算比较是拟新增能力。先在一个仓库、一个批次、一个决策人范围内试行。角色可以由同一人兼任。

| 步骤 | 谁做、在哪里做 | 可交付结果与放行条件 |
| --- | --- | --- |
| 1. 接入与校准 | 维护者选定目标仓库、解释批次与阶段的来源；插件只读预览原始值、样例及未匹配项。FD 采用标题标记，另一仓库可采用 milestone；不要求重命名或补标签 | 同一条目可点回出处。关掉映射就退回原生列表。不确定的含义由人确认，不能因零样本或权限不足推断仓库没有该阶段 |
| 2. 回顾已有批次 | 维护者先独立列待决事项，再与 Tern 的同批次、同采集范围对照。Tern 显示开放待办、关闭历史、未知项以及命中原因 | FD `830` 的采样中，#329 入待批准、#277 只入历史；用固定快照复验，不把活仓数量写成永久断言。有遗漏要能定位到取数、映射或规则；遍历未完成只出部分清单 |
| 3. 开一个新批次 | 批次负责人在团队已有的计划位置（如一条计划 Issue）明确列出**承诺项**、候选项、各项接受条件和本人确认时间。插件只在用户选择该来源后保存本机基线 | 冻结已确认的承诺 ID 清单，保存来源链接、采集时间与内容摘要。后续新增、移出和验收条件变化逐笔显示，不能刷新覆盖原基线。没有可信计划记录时只提供现状盘点，不算承诺兑现率 |
| 4. 执行与收批 | 平时沿用现有 Issue／PR 会话。收批时由验收人逐条对照原接受条件；负责人在原计划位置记录结论。插件只生成可审阅的结算草稿 | 每个原承诺恰有一个结算结果：已验收／延期／取消／未决；新增另列。已合并、已发布另附证据，不挤占验收结果。维护者无须在两个系统各维护一次状态 |

**实现切口。** `github.luau` 负责有分页与权限状态的取数；标题／milestone 到批次的映射使用不带 I/O 的规则，只接受声明式字段与匹配方式，不执行仓库提供的脚本。`host.luau` 增加回顾视图并沿用现有选中任务入口，不为管理视图另建会话系统。先不接入多个写入源，也不要求部署服务。团队仍可只用原计划位置手工开批与收批。

**权责与停止线：**

- **管理什么：** 管一个仓库中已经记录的目标、批次、交付事项和风险。跨仓依赖只引用并标明其状态来源；不承诺上游工期，不做跨项目资源调度、财务预算、人员绩效排名或通用流程编排。
- **谁有决定权：** 插件整理事实，omp 可以建议，批次负责人决定取舍，验收人确认结果。没有确认就标为建议或未决。批次试点只读；另行设计的[Issue 提交入口](requirements.md)只在报告人确认目标和最终内容后创建单条 Issue，不授权评论、打分诊标记、合并、发布或回滚。打开现有任务仍不授权写回。
- **数据放哪里：** 团队决定以原计划位置为准；个人筛选、映射及冻结基线只放插件私有数据目录，不写目标仓库。按 GitHub 主机、仓库稳定身份、批次和基线标识隔离；只保留比较所需的事项身份、接受条件、确认记录及出处，不复制评论或日志。换机或基线丢失时须从可核对的原始记录恢复，否则降级为盘点，不冒充团队共享状态。
- **执行到哪：** 打开 Issue 只读分析；打开 PR 只在核对 head 的独立工作区处理。管理决策不扩大任务权限。访问受限、目标不明、PR 版本不符或 CI 证据缺失时，停止对应动作，不妨碍浏览其他已知事实。
- **何时不推广：** 若维护者必须重复填表、关键待决项漏报、系统把未知算成完成，或换成 milestone 仓库就要重写流程，则不扩大试点。记录差异、停用相应映射，保留原 GitHub 记录与任务 worktree，不做远端“回滚”。批次管理写回和团队同步须通过开批到收批试点后独立评估；报告人提交 Issue 单独验收，不依赖批次基线。

## 一、先确定管理对象，不先规定列名

| 对象 | 最小记录 | 不能据此推断 |
| --- | --- | --- |
| 目标／路线图 | 要改善谁的什么结果、如何观察、决策人、本期不做什么 | 进入路线图不代表已承诺时间 |
| 事项 | 原始问题、接受条件、下一动作；可关联目标，也允许独立缺陷和咨询 | 被接收不代表进入本批；无人指派不代表无人跟进 |
| 批次 | 本批目标、可用人力或投入上限、承诺清单、候选清单、变更记录 | 标有批次不等于承诺交付；批次不等于版本 |
| 变更／PR | 关联事项、head、评审与检查、负责下一步的角色 | 同库编号相近不是关联；合并不代表验收或发布 |
| 发布 | 版本、渠道、目标平台、实际制品、验证证据、已知限制 | 有 release 或某平台制品，不代表某项修复在所有平台可用 |
| 决定 | 谁在何时基于什么证据决定什么，取代哪项旧决定，何时复核 | omp 的建议不能算作维护者决定 |

一个目标可以跨批次；一个事项可以拆成多个 PR；一个 PR 也可能修复多个事项。只有显式引用、原生关联或维护者确认的映射才能连线。GitHub 是其原生状态的事实来源。已有路线图 Issue、milestone 或发布说明能表达决定时直接引用；未记录的结论标未知，不要求再建一套相同文档。

## 二、运行规程：谁在什么时候决定什么

下表是推荐的最小分工，不是七场会议。单维护者可兼任各角色；多人项目指定实际决策人及代理。领域负责人可以提出方案，不等于拥有发布权限。遇到意见分歧，将选择及代价交给本项目约定的决策人；没有决策人时明确标出，不能用评论数代替决策。

| 触发点 | 主责 | 操作和出口 |
| --- | --- | --- |
| 建项、方向改变或批次回顾发现目标失效 | 项目负责人 | 明确服务对象、结果、非目标和投入边界。路线图用“现在／候选／暂不做”表达取舍；结果不可观察就先安排调查，不承诺实现。方向变化向受影响的贡献者解释原因。 |
| 新反馈、回归或需求进入 | 分诊维护者 | 先确认影响范围、复现或使用场景；咨询可直接答复，重复项链接原件，证据不足写清缺什么、等谁。可接受、拒绝、暂缓或转交；拒绝留下原因，不要求每项都开发。敏感报告转项目私有渠道，不复制到公开队列。 |
| 准备下一批／出现插队请求 | 批次负责人 | 先看现有承诺和可用人力，预留维护与突发工作余量。候选按用户影响、紧迫性、变通办法、依赖及投入讨论，不强制打综合分。只有目的、负责人、可验证的最小范围明确才作承诺；未知较多就先给调查限定投入。插队必须记录被移出或缩小的工作及理由。 |
| 已有人承接、出现依赖或 PR 反馈 | 事项负责人 | 拿下一项前先处理在制工作的卡点；超过团队可并行能力时不再开新任务。记录“被什么阻塞、等谁、到何时复看”；跨仓依赖引用具体上游事项，不能替上游承诺时间。PR 的补改、审查请求和当前版本 CI 分列；选择哪条证据就进入相应 omp 任务。 |
| 准备验收或发布 | 验收人／发布负责人 | 按原始接受条件在目标环境核验，记录版本、平台、结果。不达标回到执行；范围有变由批次负责人确认。发布前核对阻塞项、候选制品、说明、回退办法与通知对象。缺证据就暂缓，或由有权者明确记录接受的风险；按实际渠道分别确认已发布。 |
| 用户报告发布后异常 | 事件负责人 | 先界定受影响版本、平台和用户，指定沟通人；选择缓解、暂停分发、回退或修复。技术恢复后复验原场景，并向受影响用户说明结果。严重影响、数据丢失、回退或反复发生的问题进入无责复盘；每个预防动作有负责人、期限和验证办法。 |
| 批次结束或项目转入维护／停维 | 项目负责人 | 对开批承诺及中途增减逐项结算：已验收、延期、取消、未决。延期须重新选择，不自动滚入下批。对照目标看实际效果，决定继续、调整或停止；停维时说明支持范围、迁移路径和遗留事项去向。 |

**日常节奏：** 每次工作先看发布阻塞和等自己决定的事项；按团队约定定期回看等待与依赖；开批谈投入和取舍，收批谈结果和遗留风险。没有发版节拍的仓库也可以按需交付，用定期回顾替代固定迭代。紧急缺陷走快速通道，但保留批准、验证和事后记录。

## 三、每次决定只留下够用的记录

- **开批：** `批次 → 用户结果 → 可用投入 → 承诺（事项链接、负责人、接受条件）→ 候选／非目标 → 主要依赖`。没有历史开批清单的批次可以做现状盘点，不能倒推出当时承诺。
- **范围变化或风险升级：** `触发证据 → 影响哪些承诺 → 备选动作及代价 → 决定人和结论 → 通知谁／何时复核`。风险是可能发生，阻塞是已经不能推进；分别列出，不因低活跃自动升级。
- **收批／发布：** `原承诺与增减 → 验收结论 → 发布版本、渠道和证据 → 已知风险及回退负责人 → 延期／撤回理由 → 下批改进`。不必发布代码的咨询、文档决策、重复项按各自接受条件结案。

信息可以留在已有讨论或发布记录中。TernMate 显示其来源、时间和不确定性；事实冲突时并列证据。需要调整共享计划或写回 GitHub 时，由人明确指定目标和动作。队列规则、超时和进入 omp 都不是自动改标签、发评论或发布的授权。

## 五、用结果验证方法，而不是考核活跃度

| 复核问题 | 口径和使用限制 |
| --- | --- |
| 该作的决定有没有漏？ | 同一快照下，让维护者先独立圈出待决项。报告漏报、误报及原因；区分映射错误、证据缺失、真实意见分歧。不用总 Issue 数评价效果。 |
| 工作主要等在哪里？ | 分别观察等待决策、评审、外部反馈的时长。起点须是进入该状态的事件；拿不到时间就记未知，不能用最后更新时间顶替。 |
| 承诺兑现了吗？ | 以开批承诺清单为固定分母，报告其中已验收、延期、取消、未决；中途新增另列。无基线不计算兑现率；不按提交数给个人排名。 |
| 交付真的有用吗？ | 每个目标选择一个可观察结果，例如目标平台上原复现步骤不再失败、报告人确认恢复或支持请求减少。记录观察窗口和证据；没有反馈不等于成功。 |

**试行与推广：** 第一次先用 FD 830 做只读历史盘点，验证队列；下一批在开始时由维护者确认一张最小承诺清单，到结束时实际结算，补上历史样本不能检验的环节。再选一个用原生 milestone 的仓库，在不改其命名的情况下重复开批和收批。若换仓必须重写管理流程、同一决定须在两处维护，或把未知误报为完成，就修改方案再推广。当前已做 FD 数据盘点，尚未做维护者对照或跨批跟踪，不报告效率增益。

## 研究依据与取舍

- [Open Source Guides：Leadership and Governance](https://opensource.guide/leadership-and-governance/)：明确谁有权作哪种决定；不要求小项目建立委员会。
- [Basecamp Shape Up：Set Boundaries](https://basecamp.com/shapeup/1.2-chapter-03)：先定值得投入多少，再裁剪范围；不照搬六周周期，也不把投入上限当估算。
- [Kubernetes 分诊指南](https://www.kubernetes.dev/docs/guide/issue-triage/)、[Rust 优先级实践](https://forge.rust-lang.org/compiler/prioritization.html)、[VS Code 开发流程](https://github.com/microsoft/vscode/wiki/Development-Process)：分别借鉴分诊归属、有理由的定级、批次计划与验收；具体对照见[维护实践研究](maintenance-research.md)。
- [Google SRE：Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)：预先定义何时复盘，把缓解措施和预防动作分开；不把服务团队的值班制度强加给桌面项目。
