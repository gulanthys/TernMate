# TernMate 技术设计

当前入口是开发模式的 Issue／PR 浏览、任务会话与 Issue 创建，以及审核模式的只读 PR 审阅。社区收件箱、个人书签与验收、批次回顾不在当前入口中；历史试点另行标注。用户行为以[产品需求](requirements.md)为准。实现采用 [Tern Luau Block](https://docs.stencil.so/tern/guides/blocks.html)、GitHub CLI、Git 和交互式 omp，不设后端服务，不自建账户系统。

## 安装与使用

在运行 Tern 宿主的机器上准备 `git`、已登录的 `gh` 和 `omp`（支持 Tern 随附路径或宿主 `PATH`）。读取 Actions 日志需要 `gh api --help` 列出 `--allow-escape-sequences`。在插件目录执行：

```sh
tern plugin link .
tern plugin list
```

### 从 Tern 命令面板打开

入口是 **Tern 命令面板 → New TernMate**。窗口插件在当前 Tern session 的来源面板右侧分屏，不新建 tab，也不从 omp 内部启动。随后点击 Issue／PR 才启动或恢复与任务绑定的 omp 对话，不向其他对话注入消息。

**仓库从哪里来：** 命令将来源 Tern 面板已知的工作目录显式传给分屏，不读取 `omp --cwd`。`host.luau` 恢复 Block 时优先使用已保存的 checkout；新 Block 使用显式启动参数 `args[1]`，没有参数则读取 Tern 提供的 `cx.cwd`。`github.luau` 在该目录执行 `git rev-parse --show-toplevel`；仓库子目录可识别，但不递归扫描父目录。Git 根目录确定本地代码，remote 确定候选；有 fork／上游歧义时由用户选择。

**验收场景：** 从工作目录在 FluxDown 仓库内的 Tern shell 面板打开命令，同一 session 和 tab 内保留来源面板，右侧工作台识别 checkout 并列出 fork 和上游。目录缺失或不符合预期时使用 **本地 checkout…**，不从 omp 会话猜仓库。

`↑`/`↓` 移动选中项，`←`/`→` 翻到相邻页并选中该页第一项，单击或 `Enter` 打开，`Tab` 切换 Issue / PR，`/` 编辑标题关键词，`R` 刷新。快捷筛选会替换当前条件；随后仍可叠加条件或逐项移除。

共享页头显示仓库与 checkout。开发模式保留 Issue／PR 切换、创建 Issue 和复制推送命令；审核模式固定使用开放、非草稿 PR 条件，不把「待合并」当作 CI、批准或合并门禁已放行。两种模式分别保存筛选和定位，不额外查询列表。

同一 PR 的审核与开发使用不同任务键和独立 worktree。审核前核对干净的 worktree、head 和由固定 base/head 生成的差异。审核 OMP 在私有任务目录启动，必需的可信扩展 `review-guard.ts` 只注册读取、列文件和文字搜索三个工具。材料只来自本次 `review.diff`、`materials.md`；源码来自固定 head 的普通 Git blob，不遍历宿主文件系统、不跟随符号链接或子模块、不读取未跟踪文件。工具不接受 URL、通配路径或 OMP 选择器；扩展、材料或私有 Git 存储校验失败时不开始审核。

关闭工作台不删除任务材料、会话文件或 worktree；不要直接删除仍有未提交修改或本地提交的 worktree。实际目录和旧记录查看方式见下文。

## 模块与数据流

| 边界 | 输入 → 输出 | 职责 |
| --- | --- | --- |
| `plugin.toml`、`host.luau`、`window.luau` | Block 事件、本地镜像 → 视图或异步操作 | 调度后台扫描；筛选和翻页不查询远端；重新聚焦仅在回执版本变化时重扫 |
| `github.luau`、`runtime.luau` | checkout → 仓库；镜像＋筛选 → 有序行与未知项数 | 从 remote 发现仓库；纯本地匹配；提供可替换的 argv 执行接口 |
| `materials.luau` | 任务身份、版本 → 私有材料 | Issue 正文与讨论；PR 未解决线程和当前版本的 CI 证据 |
| `sessions.luau`、`session-setup.sh` | 任务身份、材料、来源面板 → 交互式 omp 面板 | 私有目录与工作树、防重、启动、聚焦和恢复 |
| `maintenance_data.luau`、`maintenance-store.sh`、`draft-store.rb` | 仓库和账号 → 分页事实、私有记录 | 核对稳定 ID；分页维护 Issue／PR 镜像与新鲜度；草稿按槽位原子比较后写入，与提交锁互斥 |
| `issue_submit.luau` | 草稿与用户明确确认 → 创建一次 Issue、核对回执 | 模板预览、一次性提交锁和结果核对 |

`inbox.luau`、`verification.luau` 和 `batch.luau` 保留早期维护视图代码，但当前 `host.luau` 不挂载这些入口。

入口使用 `--!strict`。进程调用通过一个可替换的 argv 执行函数传入；先按职责隔离，不要求每个职责都有框架或服务。

## 检索、状态与一致性

- 用 Git remote 识别候选仓库，用 `gh` 确认身份与访问权限。选定后查询显式携带 host 和 `owner/repo`；PR 编号属于 base 仓库，代码可能来自 fork。
- Issue 和 PR 筛选结果先按编号从大到小排序，再分页；不因更新时间变化重新排序。编号、状态、目标分支等条件在同一份本地镜像中取交集，不为每组条件维护远端游标。审查请求仅指直接发给当前用户的请求。筛选证据不全的候选计入未知，不报为无匹配。
- CI 证据以 `headRefOid` 为准；审查请求与 `reviewThreads.isResolved` 分开。过时行评论仍可未解决，保留原位置并标记过时。PR 生命周期状态、合并冲突、当前 head 的 CI 失败、未解决线程和请求我审查分别呈现，同一 PR 不重复成行。区分失败、进行中、通过、无检查与未知；Actions 的 PR 测试可能运行在合并提交上，须用 PR/run 关联与版本证据核对，无法对应时不引用为当前日志。
- 开发与审核列表共享当前 Block 的镜像。打开时先确认远端仓库和登录账号，再读对应的私有快照；冷启动需读完仓库历史。持久化范围是维护元数据，不是正文、讨论、CI 日志或凭据。
- 约每 5 分钟核对一次；手动 `R` 立即开始同步，扫描中的多次手动请求合并成一次后续扫描。先分别读取最新创建的 Issue 和 PR 的小批详情，后续页按创建时间倒序继续遍历。已核对的变化分批更新列表，扫描尚未覆盖的旧行继续显示；不会把部分列表当作完整镜像。首次展示每种任务的变化不等待另一种任务或磁盘写入，剩余批次合并渲染。换仓或身份失效时丢弃旧响应。
- 热扫描后续页用轻量清单核对编号、节点 ID 与版本摘要，给新增或变更节点补详情；开放 PR 另查当前 head 的检查、审查与线程，避免同一 SHA 的 CI 翻转被漏掉。缺失项须完整遍历且按 ID 复核才移除；距上次全量核对满 24 小时后做深度对账。完整同步成功才持久化镜像和新鲜度，数据不变时只更新时间戳；普通失败保留已知数据并退避，不刷新成功时间。
- PR 列表增加约 30 秒的轻量轮询：完整遍历当前开放 PR，并按节点补查镜像中原先开放但本次不在开放列表的 PR，覆盖新建、合并、关闭及同 head 的 CI／审查变化。进入 PR 列表或返回工作台也触发，正常请求间至少间隔 5 秒，失败采用指数退避。只覆盖内存展示，不写镜像或刷新全量遍历时间；后续全量遍历优先并使旧轻量请求失效。身份变化撤销旧作用域，失败不冒充空列表。
- 重试沿用最近可见的行来更新界面，仍以完整镜像校验覆盖和持久化。若历史行在失败扫描中已改变，即使新清单与完整镜像的摘要一致，也重新取详情确认。
- Issue 使用 GitHub 的 `closedByPullRequestsReferences(includeClosedPrs: true)`，分页读取明确关联并保留跨仓标识。暖扫描重新核对开放 Issue 的关系，因为关联 PR 的生命周期可能变化而 Issue 本身不动。未补读的旧缓存只显示未知，不把普通提及当作交付关联。
- PR 的 Issue 标注合并 `closingIssuesReferences` 与 `bodyHTML` 中 GitHub 已解析且 `data-hovercard-type="issue"` 的链接；只用 `href` 的 Issue 地址，不用可能指向 PR 的 `data-url`。这覆盖“关联 #522”等非关闭型引用，且排除“拆自 #1241”的 PR 链接；正文仅在内存提取，镜像只留 Issue 编号、URL 与覆盖状态。缺少该元数据的旧镜像取消新鲜度，在下一次扫描补读，不能当作无关联。
- 筛选按仓库和类型保存；选中任务按已核对的账号及仓库保留。身份失效不展示原镜像。镜像、草稿和任务记录共享以主机、稳定仓库 ID 与稳定账号 ID 为分区的契约，登录名只用于显示或当次查询；不根据它迁移旧记录。

## 启动与恢复协议

1. 任务索引另以任务类型（Issue、开发 PR、审核 PR）、编号和规范 checkout 路径区分；同一记录串行打开，不同任务不互相阻塞。列表把 `repoId`、`viewerId` 绑定到打开、恢复和复制推送命令的请求，任务层实时复查两者才查找记录；Issue 本机处理标记只查当前列表身份的记录。未绑定稳定身份的旧索引不会被读取或迁移。
2. 已有记录时，按任务目录筛出候选面板，再经 `tern process` 核对实际运行的 omp 参数和工作目录后聚焦；不使用面板标题。面板已关闭则核对确切会话文件及其中记录的任务工作目录后调用 `omp --resume`。记录或文件失效时明确提示，不用全局 `--continue` 猜测。同一身份的旧版本面板、会话文件、私有材料和 worktree 不因打开新版本而清理。
3. 首次打开为任务分配私有状态目录，用 `--session-dir` 隔离会话文件。PR 材料区分 Conversation 评论、已提交的整体 review 正文、未解决的行内线程和当前版本 CI；讨论或整体 review 未读全时标明覆盖，超长段落标记截断。Issue 和开发 PR 的初始消息使用 `@材料文件`；审核 PR 只通过受限证据工具读取。
4. Issue 和 PR 都用 `tern new tab <来源 session ID>`，显式指定来源窗口，在私有任务目录启动 omp。Issue 和开发 PR 的 `--cwd` 指向 worktree；审核的 `--cwd` 和恢复时校验的会话目录均为私有任务目录，不从 PR 代码发现工具。在多个窗口中无法唯一确定来源时不启动。首次发出中文任务指令，恢复时不重发。确认实际进程后记录面板身份，并保存唯一可验证的会话文件路径。
5. 不写全局 OMP 配置。Issue 和 PR 新建、恢复均由 OMP 按正常配置优先级决定审批模式。PR 保留 `pr-safety.yml` 和禁用自动加载的参数，不从未绑定稳定身份的旧记录恢复进程。
6. 重开当前版本的 PR 只刷新评论，不重复查 CI。按评论节点 ID 与首轮及已排队记录去重；确认仓库、账号、版本和原 `.jsonl` 后原子写入私有队列。显式加载的 OMP 扩展等待确切会话空闲，通过消息 API 开始分析，不向终端发送按键、不改动编辑框。未投递批次保留以供恢复，回执与会话记录避免重复投递。升级前启动的 PR 进程退出后才加载扩展。

## Issue 工作区

- 首次打开从所选 GitHub 仓库拉取 `refs/heads/main`，以拉取到的提交创建 linked worktree 和 `ternmate/issue-<编号>-<标识>` 本地分支。网络拉取使用临时 Git 库，导入不更新源 checkout 的 `FETCH_HEAD` 或远端跟踪分支；拉取失败不回退到本地提交。创建时关闭 Git hook 和子模块递归，发现本地 checkout filter 命令则拒绝创建。
- 列表区分已打开的本机会话、对话记录与待启动工作区。选中时在宿主后台检查该账号、checkout 和 Issue 对应的任务 worktree，验证所有权后读取相对初始提交的 HEAD 与工作区状态；配置含可执行清洗过滤器时不运行状态检查。没有写入 Git 索引，也不据此推断验收或远端推送状态。
- 点击仍只授权分析；用户明确要求修复后，编辑限定在该 Issue 的 worktree。再次打开沿用已绑定的会话和工作区，不随 `main` 前移重建。未绑定稳定身份或使用共享 checkout 的旧 Issue 会话不改写路径或历史，也不由工作台恢复。

## PR 工作区与安全边界

- 从目标仓库以 HTTPS 获取 `refs/pull/<number>/head`，核对实际提交与查询的 head SHA。每个版本使用新建的私有 Git 存储、独立 worktree 和 `ternmate/pr-<编号>-<标识>` 本地分支，不继承原 checkout 的 Git 配置、引用、hook 或 filter。恢复不切换用户分支，不改索引。
- 开发 PR 以 head SHA 区分版本；审核 PR 以 `(baseRefName, base SHA, head SHA)` 区分版本。同 head 换目标分支或 base 提交即产生新的审核版本；不能把旧 `review.diff` 当作当前差异。
- 普通打开按实时查询到的当前版本开始准备；若材料与当前版本不一致、取到的 head 改变，或在启动前复查时版本变化，重新显示版本提示。确认打开当前版本时核对选定的精确版本，失效则显示新提示，不启动替代版本。审核版本提示包括目标分支、base 和 head；有可核对的旧版本时，可从提示选择该版本的既有记录。旧工作区、材料、对话和运行中的面板不受影响。
- Issue 内容、审查评论、日志和 PR 代码按不可信数据处理，不授予执行指令的权力。worktree 是修改隔离，不是执行沙箱；即使 OMP 配置自动批准工具调用，也不授权 GitHub 写入，不改变执行外部脚本前核对信任的要求。只使用已有 `gh` 登录态；第三方 CI 无法读取日志时提供检查链接并标记证据缺失。
- GitHub CLI 的终端转义豁免只用于捕获已验证 job 的日志，不直出到面板；插件剥离 ANSI 格式、跳过其他终端序列，仅把脱敏、限长且标记截断的相关失败行交给 omp。私有材料不写入仓库，关闭面板不删除 worktree。
- 已合并 PR 可显式预览并清理所选工作区。预览与确认分别在线核对仓库、账号、PR 合并状态及 head，确认时与同任务的打开操作串行，并拒绝 Tern 中仍被占用的工作区。私有 Git 存储、分支与初始提交必须匹配；有工作区文件、锁或非标准索引标记时不执行。用无 `--force` 的 `git worktree remove` 和带预期 OID 的引用删除；保留对象库、材料和会话。私有清理标记允许下次从原提交重建并继续原会话，不覆盖现存文件或已变化的分支。
- 批量清理以当前「已合并」筛选的完整结果集为范围，先从该账号和 checkout 查找本机任务记录，再逐个核对并生成预览。确认只处理预览中可清理的条目，逐项复用单项清理门禁；单项跳过不影响其余条目，结果保留具体原因。

## 本机数据与隔离

Tern 在其宿主的 [状态目录](https://docs.stencil.so/tern/concepts/packages.html#directories) 下分配 `plugin-data/ternmate/`（Lua 中的 `tern.plugin.data`）。macOS 默认是 `~/Library/Application Support/Tern/plugin-data/ternmate/`；宿主设置了 `TERN_CONFIG_DIR` 时使用 `$TERN_CONFIG_DIR/plugin-data/ternmate/`，不是插件源码或任务 checkout。

| 当前数据 | 插件数据目录下的路径 |
| --- | --- |
| 镜像 | `maintenance-mirror-v1/<身份>/snapshot.json`；同内容核对的成功时间原子写入 `snapshot.checked`。新鲜度须对应当前快照和该身份最新的不可覆盖提交结果；旧快照仍可作为基线 |
| Issue 草稿与提交回执 | `maintenance-v2/<身份>/submit-*.json` |
| 任务材料、omp 会话、工作区 | `task-sessions-v2/`；索引在 `kv.json`，以稳定身份键区分，不沿用旧键 |

`<身份>` 由小写 GitHub 主机、仓库稳定 ID、账号稳定 ID 的字节十六进制编码组成，各段用 `-` 分隔。账号改登录名不改变新分区。

Issue 模板或标签请求失败、创建助手无法确认凭据时，先隐藏草稿并重新核对账号和仓库，核对通过后才可重新预览。保存草稿、确认丢弃和关联网页原件都在同一把槽位锁内比较草稿；旧确认不会移除新版，保存冲突会保留当前输入。直接创建、事后核对和首次关联网页原件都独占保存回执，不依赖镜像目录可写；并发确认只有一个写入者。镜像从同身份最高的已结算槽位派生版本（明确拒绝也保守地更新版本）。旧扫描不能在新回执落盘后刷新成功时间；发现版本变化立即重扫，不走普通错误退避。重新聚焦时先本地核对版本；首次读取缓存途中收到聚焦事件，须在显示准确计数前补做核对。重看历史回执不触发刷新。

网页关联的回执先独占保存，再清理同一槽位的私有草稿。恢复时核对回执的 Issue ID、编号、标题、状态、创建时间及当前仓库的 Issue URL；记录不完整或不匹配时保留草稿并提示。沿 `maintenance-v2` 的连续槽位链恢复时，也清理旧版已跳过的有效外部回执槽位，不删除后继草稿或其他类型的历史草稿。历史清理失败不阻塞当前草稿，重新读取本地记录时重试；当前回执清理失败则保留回执并提供重试，清理完成前不开放下一份草稿。普通聚焦核对期间的再次聚焦合并成一次补查，期间不恢复准确计数。

### 旧记录只读查看

工作台没有旧记录查看或迁移界面。若原文件仍在，可在对应 Tern 宿主上用本地只读查看器（如 `less`）查看：

- `maintenance-v1/<旧分区>/`：旧草稿／回执为 `submit-*.json`，个人书签为 `verify-bookmark-*.json`，验收历史为 `verify-records-entry-*.json`，批次记录为 `batch-*.json`。旧分区末段编码的是小写登录名，不是稳定账号 ID。
- `task-sessions-v1/`：历史任务材料、会话 `.jsonl` 及 worktree；本机 Tern 的 `kv.json` 中可能仍有对应 `session-v1:` 旧索引。没有文件时，不能据此恢复已经被旧版清理的对话。

这些文件可能包含私有内容，也不是迁移凭据。保留原件，不把它们复制或改名到新分区，不编辑索引来恢复身份。旧 Issue 提交结果未知时先在原 GitHub 仓库只读核对，不拿旧草稿重新提交。

## 历史维护视图设计（非当前入口）

以下保留早期试点的设计，不是当前工作台的操作说明。社区收件箱、个人验收和批次回顾不挂载；当前可用的 Issue 创建另见[Issue 提交协议](#issue-提交协议独立写入功能)。

试点目标是执行[项目管理手册](project-management.md)中的开批、跟进、收批；相关接手信号和按环境验收规则见[开源维护工作台设计方案](open-source-workbench.md)。批次不是第三种 GitHub 任务，也不要求每个阶段都是可拖动的看板列。

### 面板与操作

- 在仓库标题旁增加「批次回顾」按钮。首次进入选批次来源：使用原生 milestone，或预览并确认仓库标题标记映射。显示命中样例和未匹配样例；可以跳过并返回普通浏览。记住每个仓库上次选择的批次，不擅自取最大数字为当前批次。
- 回顾页顶部固定显示仓库、批次选择器、扫描状态、基线状态。主区域用可换行的队列按钮和单列事项列表，不依赖宽屏多栏。队列包括「待决策」「待排期」「执行卡点」「等反馈」「待核对」「历史」；保留「全部」以便找到未映射项。队列可重叠，总项数按 Issue 身份去重。已关闭的事项进入历史；如果已有开批承诺但缺验收，其结算页仍须显示未决。
- 每行展示 `#编号 标题`、命中原因和下一行动角色，保留独立的「依据」按钮。点依据只展开原始标记、来源链接和关联 PR；点 Issue 行或按 Enter 直接进入 Issue 的 omp 分析；点具名 PR（如 `处理 PR #1183`）才进入其工作区。有多个 PR 全部列出，不猜一个。回到面板保留批次、队列、选中项。`Esc` 先收起依据，再回任务浏览；保留现有浏览页的 `Tab` 行为。
- 页底管理动作限定为「记录开批基线」「比较并生成结算草稿」。无基线时明确写“仅盘点”；无权访问、限流、游标未走完或确认来源不完整时，显示已读范围和原因，禁用涉及该范围的最终结算。看历史批次不弹窗要求补录计划。

### 基线不是实时列表的副本

开批时先定位团队已有的计划来源，预览事项、承诺／候选划分和接受条件。**由维护者逐项确认承诺后**冻结初始记录；任意自由文本不自动解析成承诺。只在本机私有插件目录保留比较所需字段：主机、仓库稳定 ID、批次、基线 ID、来源及版本依据、确认时间、事项稳定 ID 和当时的接受条件。候选不计入承诺分母。视图和筛选偏好可覆盖，基线不可被刷新覆盖；显式更正须保留所替代的版本。

收批比较开批集合与当前证据：中途新增、移出和条件变化分别列出；改标题或换批次不抹去原承诺。远端关闭只说明结案，不替代验收决定。结算输出为可复制的 Markdown 草稿，逐项注明已验收／延期／取消／未决及依据；本机丢失基线又无法从原始计划版本复核时，只输出盘点。插件不发布草稿、不修改团队计划。

### 防止重复确认和错误结算

- **区分三类记录。** 远端事实按来源刷新；团队决定须能定位到计划或验收记录；本机保存的是这些记录的比较快照，不是另一份团队决定。确认保存的本机用户不能被当作远端决定人。编辑过的评论若没有可核对的旧版本，本机快照只证明当时读到了什么。
- **写入边界。** 开批采用“预览 → 明确确认 → 原子保存”。同一仓库、批次与来源版本只创建一次；两个面板同时确认时，后者重读已有基线并展示差异，不覆盖。保存失败停在预览并提示原因；私有目录不可用时仍能只读盘点。仓库或来源身份发生变化须重新核对，不自动沿用基线。
- **结算算法按身份，不按标签计数。** 先取初始承诺 ID 集，再并入经确认的新增项；即使迁出本批、改标题或关闭，也按 ID 回查初始项。没有权限读回的项仍占原分母，标「未决：不可读」。移出事实不等于延期或取消，由决定依据区分。一个事项的多个 PR 或多个平台不会增加承诺数。
- **可复核的草稿。** 标题列仓库、批次、基线标识、比较时间和覆盖范围；正文先列原承诺的已验收／延期／取消／未决，再列新增及其结果、尚未确认的变更、发布和复盘。每项链接其依据；不含 omp 对话、原始日志、凭据或私有任务材料。没有团队确认的结算来源，标题始终保留「草稿」。

### 用一条变化链验收而不只测单个页面

以下是用于实现验收的**假设案例**，不是 FD 的实际管理决定。开批时 A、B 两项被承诺，C 是候选；中途负责人确认 C 插队并决定 B 延期，A 的 PR 合并但目标平台尚未验证。刷新后，原承诺仍为 A、B：A 未决、B 延期；C 单列新增。若此时 B 已换了标题批次，也不能从原承诺消失。随后 A 有验收记录，则变为已验收；若只查到 Windows 制品，不能替其他目标平台宣告已交付。若发布后又出现回归，新反馈进入分诊或执行，历史验收仍注明原平台和版本。

相邻场景一并验收：双面板同时开批只生成一个基线；中断扫描不显示全批结论；无共享计划的个人项目只盘点；复制草稿后 GitHub 与原工作区不变。上述管理路径须在真实 Tern 面板走通，不能以文档完成或单个纯函数通过代替端到端验收。

## Issue 提交协议（独立写入功能）

**目标与权限。** 开发模式的「新建 Issue」打开本地编辑器，不调用写 API。草稿按 GitHub 主机、仓库和账号稳定 ID 分区，关联模板版本，存于仅当前用户可读的插件目录，提供继续、丢弃两种明确操作；草稿不属于 omp 会话。选仓时显示 fork／上游及可见性，预览后若切换目标、账号、模板或正文，旧确认失效。Issue 功能关闭或无法确认身份时保留草稿，不试投其他仓库。

**尊重仓库入口。** 读取目标默认分支的 Issue 模板和 `config.yml`，遵守禁用空白表单、必填、枚举、标题前缀和联系渠道。FD 的 Bug 表单收集 Version、OS、Protocol 与复现；功能建议表单收集场景、方案与 Scope。版本字段不得生成处理批次，`triaged`、`roost:*` 等维护动作不从报告内容推断。查重只向已确认目标主机查询用户可见并同意检索的标题关键词，不发送整段草稿；列开放和关闭候选，不自动合并、评论或阻止新建。

**两条提交路径。** 能完整呈现且不需额外管理动作的表单可在插件内编写；确认页显示主机、仓库、账号、可见性、最终标题和正文。创建助手从宿主已有 `gh` 登录态通过私有管道获取一次凭据，用它核对账号和仓库的稳定 ID，再用同一凭据调用一次 `createIssue`。mutation 按预览绑定的仓库和标签 ID 提交，不按可能已变化的名字猜测。凭据不上屏、不写文件。无法等价呈现模板、要求附件或涉及敏感报告时，转向受信的仓库原生入口；由用户在那里填写并提交，不把草稿拼入 URL。打开网页不算成功，可通过“关联已创建 Issue”提供 URL 并回查身份。

**一次提交的生命周期。** 预览、身份校验和草稿准备不创建发送锁，关闭或撤销面板不会因丢弃这些回调而留下未知提交。独立助手完成校验后，在可能发出 mutation 前独占写入发送锁；只有获锁者能发送。助手独立保存已验证的回执或明确未发送／被拒绝的结果，不依赖面板仍开着。越过发送门禁后如果进程中断且没有结果，按可能已发送处理。按仓库、作者、时间与标题只读找候选，让用户确认具体原件；零结果不证明创建失败，不能重发未知提交。

**交给谁、怎样回来。** 回执提供“查看原件／在 omp 分析／返回列表”；当前筛选若排除新单，提示原因而不重置筛选。分诊依据仓库实际状态，机器人若已经处理，不再强行标“待分诊”。报告人通过「我创建的」或原链接查看需补材料、复测请求、后续关联 PR 和有证据的版本；回复或关闭仍由用户在有权限的渠道完成。没有回复不可视为验收通过。

**放行条件。** 在专用测试仓库验证 fork／上游选对、FD 风格必填表单、禁止空白、原生网页交接、查到已关闭相似项后仍可报告回归；预览和取消零写入，双击只建一条，创建成功但客户端丢响应时核对原件而非再建。最后以同一编号走通创建、分诊、关联修复、回到报告人复测。禁止用真实 FD 仓库试发测试工单。
