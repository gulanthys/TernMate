# TernMate 技术设计

状态：已实现任务浏览、社区收件箱、Issue 创建、个人验收和批次回顾。用户行为以[产品需求](requirements.md)及[开源维护工作台](open-source-workbench.md)为准。采用 [Tern Luau Block](https://docs.stencil.so/tern/guides/blocks.html)、GitHub CLI、Git 和交互式 omp，不设后端服务，不自建账户系统。

## 安装与使用

在运行 Tern 宿主的机器上准备 `git`、已登录的 `gh` 和 `omp`（支持 Tern 随附路径或宿主 `PATH`）。读取 Actions 日志需要 `gh api --help` 列出 `--allow-escape-sequences`。在插件目录执行：

```sh
tern plugin link .
tern plugin list
```

### 从 Tern 命令面板打开

入口是 **Tern 命令面板 → New TernMate**。窗口插件在当前 Tern session 的来源面板右侧分屏，不新建 tab，也不从 omp 内部启动。随后点击 Issue／PR 才启动或恢复与任务绑定的 omp 对话，不向其他对话注入消息。

**仓库从哪里来：** 命令将来源 Tern 面板已知的工作目录显式传给分屏，不读取 `omp --cwd`。`host.luau` 恢复 Block 时优先使用已保存的 checkout；新 Block 使用显式启动参数 `args[1]`，没有参数则读取 Tern 提供的 `cx.cwd`。`github.luau` 在该目录执行 `git rev-parse --show-toplevel`；仓库子目录可识别，但不递归扫描父目录。Git 根目录确定本地代码，remote 确定候选；有 fork／上游歧义时由用户选择。

**验收场景：** 从工作目录在 FluxDown 仓库内的 Tern shell 面板打开命令，同一 session 和 tab 内保留来源面板，右侧工作台识别 checkout 并列出 fork 和上游。目录缺失或不符合预期时使用 **本地 checkout…**，不从 omp 会话猜仓库。

`↑`/`↓` 移动选中项，单击或 `Enter` 打开，`Tab` 切换 Issue / PR，`/` 编辑标题关键词，`R` 刷新。快捷筛选会替换当前条件；随后仍可叠加条件或逐项移除。

插件数据目录下的 `task-sessions-v1/` 保存私有任务材料、omp 会话和 PR worktree。关闭面板不删除这些文件；不要为清理空间直接删除其中仍有未提交修改或本地提交的 worktree。

## 模块与数据流

| 边界 | 输入 → 输出 | 职责 |
| --- | --- | --- |
| `plugin.toml`、`host.luau`、`window.luau` | Block 事件 → 视图或异步操作 | 列表、筛选、进度、错误及桌面焦点刷新；`view` 不做 I/O |
| `github.luau`、`runtime.luau` | 本地路径、目标仓库、类型、条件 → 分页条目 | 发现 checkout 和远端仓库；通过 `gh` 查询列表；提供可替换的 argv 执行接口 |
| `materials.luau` | 任务身份、版本 → 私有材料 | Issue 正文与讨论；PR 未解决线程和当前版本的 CI 证据 |
| `sessions.luau`、`session-setup.sh` | 任务身份、材料、来源面板 → 交互式 omp 面板 | 私有目录与工作树、防重、启动、聚焦和恢复 |
| `maintenance_data.luau`、`maintenance-store.sh` | 仓库和账号 → 分页事实、私有记录 | 核对账号和仓库稳定 ID；按两层游标读取 Issue／PR，独占创建记录或追加历史 |
| `inbox.luau`、`verification.luau` | GitHub 事实、个人验收 → 收件箱和依据 | 区分原始状态、可核实的下一动作、私有书签和限定范围的复测结论 |
| `issue_submit.luau`、`batch.luau` | 明确用户决定 → 一次 Issue 创建或本机计划记录 | 预览、一次性提交锁和回执；确认批次来源、冻结基线并复制结算草稿 |

入口使用 `--!strict`。进程调用通过一个可替换的 argv 执行函数传入；先按职责隔离，不要求每个职责都有框架或服务。

## 检索、状态与一致性

- 用 Git remote 识别候选仓库，用 `gh` 确认身份与访问权限。选定后查询显式携带 host 和 `owner/repo`；PR 编号属于 base 仓库，代码可能来自 fork。
- 列表按更新时间倒序，编号作为稳定次序。精确编号直查并校验类型与其他条件。状态和 PR 目标分支在 GitHub 侧筛选；其余条件在游标遍历时取交集。审查请求指直接发给当前用户的请求，不把团队请求算作个人请求。候选页携带线程和 CI 摘要，需继续遍历的嵌套连接走独立游标。找到当前显示页后可暂停，继续加载时沿游标推进。
- 以 `headRefOid` 标识 PR 版本；审查请求与 `reviewThreads.isResolved` 分开。过时行评论仍可未解决，保留原位置并标记过时。读取当前提交的检查及状态；区分失败、进行中、通过、无检查与未知。Actions 的 PR 测试可能运行在合并提交上，须用 PR/run 关联与版本证据核对；无法对应时不引用为当前日志。
- 每次切换仓库、条件或刷新都递增查询代号；迟到的回调不得覆盖新视图。切回列表时刷新；仅查询摘要，进入任务后才取正文、讨论和失败日志。限流时显示已加载范围与可重试时间，不持续轮询。
- 每个仓库和列表类型保存筛选、排序位置及选中条目的稳定键，不持久化整张列表。面板保存值只含 UI 恢复所需数据；跨面板的会话索引单独保存，不把 token、评论或日志写入索引。

## 启动与恢复协议

1. 任务键取 `(host, owner/repo, issue|pr, number)`；本地会话记录另绑定 checkout 身份，避免两个本地副本误用工作区。对同一记录串行执行打开操作。不同任务不互相阻塞。
2. 已有记录时，按任务目录筛出候选面板，再经 `tern process` 核对实际运行的 omp 参数和工作目录后聚焦；不使用面板标题。面板已关闭则核对确切会话文件及其中记录的 checkout 后调用 `omp --resume`。记录或文件失效时明确提示，不用全局 `--continue` 猜测。再次打开 PR 时检查远端版本变化。
3. 首次打开为任务分配私有状态目录，用 `--session-dir` 隔离会话文件。材料分别保存出处、正文、讨论、审查及 CI 证据；超长段落标记截断。启动参数使用固定任务说明与 `@材料文件`，不把远端文本拼进命令。
4. 宿主按 argv 调用 `tern split <来源面板> right --cwd <私有启动目录> -- omp --cwd=<工作目录> …`，并显式指定来源窗口；在多个窗口中无法唯一确定来源时不启动。私有启动目录避免在启动阶段加载 PR 的 `.env`。确认实际进程后记录面板身份；确认生成唯一会话文件后原子保存恢复路径。

## PR 工作区与安全边界

- 从目标仓库以 HTTPS 获取 `refs/pull/<number>/head`，核对实际提交与查询的 head SHA。每个版本使用新建的私有 Git 存储及其 detached worktree，不继承原 checkout 的 Git 配置、引用、hook 或 filter，也不在原 checkout 执行 checkout、reset 或清理。
- 恢复时分别检查上游 SHA、工作区 HEAD、未提交修改。远端变化时显示新旧 SHA；选择旧版本只继续界面明确显示的版本，不改用其他面板最近打开的版本。选择新版本则在再次核对远端后创建独立工作区。即使旧工作区干净，也不会丢弃本地提交。
- Issue 内容、审查评论、日志和 PR 代码均不可信。外部内容作为带来源的数据，不授予执行指令的权力。worktree 是修改隔离，不是执行沙箱；对外部贡献的 PR，执行仓库脚本前确认信任或在无凭据的隔离环境运行，不开启 omp 自动批准。只使用已有 `gh` 登录态；第三方 CI 无法读取日志时提供检查链接并标记证据缺失。
- GitHub CLI 的终端转义豁免只用于捕获已验证 job 的日志，不直出到面板；插件剥离 ANSI 格式、跳过其他终端序列，仅把脱敏、限长且标记截断的相关失败行交给 omp。私有材料不写入仓库，关闭面板不删除 worktree。

## 验证

- macOS Tern 0.9.28 隔离窗口：从 fork 选择上游；标题筛选命中首屏之外的 Issue；单击后 omp 收到来源、正文和讨论，首轮回复后原 checkout 无变化；重复打开聚焦原面板，关闭后从确切文件恢复。
- 同一窗口实测公开 PR `cli/cli#14927`：列表同时标出未解决线程和当前失败 CI；连按 Enter 只启动一个 omp。材料包含 4 条未解决线程、失败 job 和 step、3 行无终端转义的日志摘录。worktree HEAD 等于 PR head，原 checkout 保持不变；切回 Issue 保留筛选和选中项。
- 在隔离窗口注入变化后的 head 响应：面板显示新旧两组 SHA；材料仍属旧 head 时拒绝启动新版本；选择旧版本聚焦原会话，保留旧 worktree 的本地提交及未提交文件。
- Shell 通过 `/bin/sh -n`，Luau 通过 `luau-lsp analyze`。未实测 GitHub 上实际发生的 head 更新及跨窗口消歧；未执行该外部 PR 的脚本，也未写入 GitHub。
- macOS Tern 0.9.29：真实 FluxDown 只读扫描完成，社区收件箱显示 1197 项；批次回顾预览标题映射并打开 830，无基线时显示「仅盘点」。真实模板页显示禁用空白 Issue、官网反馈、FAQ 和投票渠道。
- 隔离 Tern 窗口接本地 GitHub CLI 测试替身：必填字段阻止预览，预览和取消不创建，双击只调用一次创建并核对回执；模拟回执丢失后重进仍是「结果待核对」，没有普通重试。
- 同一隔离窗口：给开放 Issue 的两个症状分别记通过与受限，两种队列均保留证据；用原生 milestone 冻结基线，模拟原承诺移出、关联 PR 合并和中途新增，结算仍显示原承诺 1、已验收 0、未决 1，新增与移出各 1。独占写入在并发测试时只有一个成功。
- 维护模块通过 `luau-lsp analyze`，存储脚本通过 `/bin/sh -n`。本轮未向 GitHub 发送写请求，未实测远端创建或独立维护者对照验收。

## 项目维护视图

开源项目的默认入口、接手信号和按环境验收规则见[开源项目维护工作台设计方案](open-source-workbench.md)；以下批次视图是可选层，不是提交或处理贡献的前置条件。

目标是执行[项目管理手册](project-management.md)中的开批、跟进、收批。**一个 Block，两种入口：**「任务浏览」保留现有 Issue／PR 列表和快捷键；「批次回顾」回答这一批需要做哪些决定。回顾不是第三种 GitHub 任务，也不是把每个阶段都做成可拖动的看板列。

### 面板与操作

- 在仓库标题旁增加「批次回顾」按钮。首次进入选批次来源：使用原生 milestone，或预览并确认仓库标题标记映射。显示命中样例和未匹配样例；可以跳过并返回普通浏览。记住每个仓库上次选择的批次，不擅自取最大数字为当前批次。
- 回顾页顶部固定显示仓库、批次选择器、扫描状态、基线状态。主区域用可换行的队列按钮和单列事项列表，不依赖宽屏多栏。队列包括「待决策」「待排期」「执行卡点」「等反馈」「待核对」「历史」；保留「全部」以便找到未映射项。队列可重叠，总项数按 Issue 身份去重。已关闭的事项进入历史；如果已有开批承诺但缺验收，其结算页仍须显示未决。
- 每行展示 `#编号 标题`、命中原因和下一行动角色，保留独立的「依据」按钮。点依据只展开原始标记、来源链接和关联 PR；点 Issue 行或按 Enter 直接进入 Issue 的 omp 分析；点具名 PR（如 `处理 PR #1183`）才进入其工作区。有多个 PR 全部列出，不猜一个。回到面板保留批次、队列、选中项。`Esc` 先收起依据，再回任务浏览；保留现有浏览页的 `Tab` 行为。
- 页底管理动作限定为「记录开批基线」「比较并生成结算草稿」。无基线时明确写“仅盘点”；无权访问、限流、游标未走完或确认来源不完整时，显示已读范围和原因，禁用涉及该范围的最终结算。看历史批次不弹窗要求补录计划。

### 基线不是实时列表的副本

开批时先定位团队已有的计划来源，预览事项、承诺／候选划分和接受条件。**由维护者逐项确认承诺后**冻结初始记录；任意自由文本不自动解析成承诺。只在本机私有插件目录保留比较所需字段：主机、仓库稳定 ID、批次、基线 ID、来源及版本依据、确认时间、事项稳定 ID 和当时的接受条件。候选不计入承诺分母。视图和筛选偏好可覆盖，基线不可被刷新覆盖；显式更正须保留所替代的版本。

收批比较开批集合与当前证据：中途新增、移出和条件变化分别列出；改标题或换批次不抹去原承诺。远端关闭只说明结案，不替代验收决定。结算输出为可复制的 Markdown 草稿，逐项注明已验收／延期／取消／未决及依据；本机丢失基线又无法从原始计划版本复核时，只输出盘点。插件不发布草稿、不修改团队计划。

### 分段验收

1. **只读盘点先验收。** 固定 FD 830 快照，#329 在待批准、#277 在历史；未读完的页不报总数。换到 milestone 仓库，不修改标题也可得到同一视图。
2. **入口不能串任务。** 对无批次的 #1180／#1183 单独核验：不混入 830；有明确关联时从 Issue 点具名 PR，应在该 PR 的正确 head 打开。已有的 Issue／PR 浏览、筛选与会话不受影响。
3. **再验收开批与收批。** 用含新增、移出、改条件和已合并未验证的一个真实批次，对照维护者独立清单；确认原承诺不丢、未知不算完成、无远端写入。通过前不将结算作为团队报告。

### 一轮维护在 Block 中怎样走完

不为每个阶段新增导航页。**入批前的事留在「任务浏览」，有批次的取舍留在「批次回顾」，跨阶段的事实放在同一个「依据」面板。** 从回顾跳到任务浏览核对依赖时保留返回位置；不把被查看的事项顺手加入本批。每次交接至少能回答：来自哪条记录、下一步由哪个角色做什么、还差什么证据。不能回答的部分明确留空。

| 阶段 | 入口与可做的事 | 交接条件；不满足时怎么办 |
| --- | --- | --- |
| 目标与接入 | 在回顾页的批次选择器旁查看「范围与目标」：来源、目标用户、希望观察到的结果、非目标和决策人。路线图条目只按明确引用关联，可返回任务浏览查看原件 | 目标不明仍可浏览；只允许做范围盘点，不把路线图或版本标题转成日期承诺。没有批次机制的项目可一直使用任务浏览 |
| 反馈与提交 | 任务浏览 → 新建 Issue；验收／发布反馈也能新建草稿。选择模板、查重、补全信息、预览并确认一次创建。详见下文「Issue 提交协议」 | 有回执才成为远端事项；草稿不进队列，疑似重复可转向原件，结果未知不得重发。外部渠道已创建的 Issue 直接进入分诊，不要求经插件重提 |
| 需求分诊 | 在任务浏览选择「待分诊／待补充」，单击 Issue 只读分析。依据面板区分问题类型、影响、报告版本、处理批次和待答角色 | 有接受决定才进候选；缺复现进入等反馈；暂缓留下重看条件。咨询、重复或拒绝可以在来源中给出答复、原件或理由后结案，无须虚构 PR。敏感事项不进入可复制的公开摘要 |
| 开批承诺 | 批次回顾 →「记录开批基线」→ 指定计划来源 → 预览候选与明确承诺 → 核对范围、接受条件与决定出处 → 确认保存到本机。确认页展示哪些候选**不会**进入分母 | 预览或取消不产生基线；缺接受条件或来源的事项留在候选。已有基线时优先打开现有记录，不因再次进入、切仓或刷新创建新基线 |
| 执行与变更 | 从卡点行选择具名 Issue／PR 进入 omp；可在依据面板查看一个事项的多个 PR 及其不同 head。切回时重新取事实，不丢选中项 | 审查要求修改、未决线程、失败检查分别作证据。出现插队或移出时列出与原计划的差异；只有负责人在计划来源确认后才是已批准变更，否则写“发现范围差异，待确认” |
| 验收与退回 | 在承诺事项的依据面板逐项对照「原接受条件／实际结果／环境和版本／验收出处」。验收人查看已有记录；不让维护者在插件里重复批准 | 符合条件且有验收决定才记已验收。失败要列出哪条不符并提供返回任务入口；PR 合并或 Issue 关闭而缺证据时仍为未决。验收条件有变时同时呈现前后版本和谁批准，不能悄悄放宽 |
| 发布与反馈 | 在已验收条目按需展开发布依据，列明目标渠道、平台、制品和来源；从实际反馈条目回到任务浏览。不是每个批次都需要发版 | 按平台分别报告可用性；有 tag 无目标制品、或变更与发布无明确关联时标未知。回归进入新的跟进事项或引用重开的原件；阻断当前交付须有负责人决定，不能由插件发布或回滚 |
| 收批与结算 | 批次回顾 →「比较并生成结算草稿」→ 先看未决与取数缺口，再看承诺逐项结果、中途变化及发布证据。维护者可复制草稿，在原计划位置自行确认 | 已确认初始范围且扫描完整，才给完整范围结算；其中允许有明确标出的未决事项。无基线只出盘点；关键页不可读只出带警示的部分草稿。复制不等于团队批准、关闭 Issue 或发布 |
| 复盘与下批 | 从结算查看未兑现理由、发布后回归、预防动作的责任人和验证方式。用既有跟进 Issue 作出处；无记录时列为待决定建议 | 延期是本批结果，不是下批承诺。新批次须重新选择；停止维护时记录支持范围和遗留项去向，不自动迁移。历史结算引用当时证据，新反馈补充复盘，不覆盖过去的快照 |

### 防止重复确认和错误结算

- **区分三类记录。** 远端事实按来源刷新；团队决定须能定位到计划或验收记录；本机保存的是这些记录的比较快照，不是另一份团队决定。确认保存的本机用户不能被当作远端决定人。编辑过的评论若没有可核对的旧版本，本机快照只证明当时读到了什么。
- **写入边界。** 开批采用“预览 → 明确确认 → 原子保存”。同一仓库、批次与来源版本只创建一次；两个面板同时确认时，后者重读已有基线并展示差异，不覆盖。保存失败停在预览并提示原因；私有目录不可用时仍能只读盘点。仓库或来源身份发生变化须重新核对，不自动沿用基线。
- **结算算法按身份，不按标签计数。** 先取初始承诺 ID 集，再并入经确认的新增项；即使迁出本批、改标题或关闭，也按 ID 回查初始项。没有权限读回的项仍占原分母，标「未决：不可读」。移出事实不等于延期或取消，由决定依据区分。一个事项的多个 PR 或多个平台不会增加承诺数。
- **可复核的草稿。** 标题列仓库、批次、基线标识、比较时间和覆盖范围；正文先列原承诺的已验收／延期／取消／未决，再列新增及其结果、尚未确认的变更、发布和复盘。每项链接其依据；不含 omp 对话、原始日志、凭据或私有任务材料。没有团队确认的结算来源，标题始终保留「草稿」。

### 用一条变化链验收而不只测单个页面

以下是用于实现验收的**假设案例**，不是 FD 的实际管理决定。开批时 A、B 两项被承诺，C 是候选；中途负责人确认 C 插队并决定 B 延期，A 的 PR 合并但目标平台尚未验证。刷新后，原承诺仍为 A、B：A 未决、B 延期；C 单列新增。若此时 B 已换了标题批次，也不能从原承诺消失。随后 A 有验收记录，则变为已验收；若只查到 Windows 制品，不能替其他目标平台宣告已交付。若发布后又出现回归，新反馈进入分诊或执行，历史验收仍注明原平台和版本。

相邻场景一并验收：双面板同时开批只生成一个基线；中断扫描不显示全批结论；无共享计划的个人项目只盘点；复制草稿后 GitHub 与原工作区不变。上述管理路径须在真实 Tern 面板走通，不能以文档完成或单个纯函数通过代替端到端验收。

### Issue 提交协议（独立写入功能）

**目标与权限。** 「新建 Issue」打开本地编辑器，不调用写 API。草稿绑定 GitHub 主机、仓库稳定身份、账号及模板版本，存于仅当前用户可读的插件目录，提供继续、丢弃两种明确操作；草稿不属于 omp 会话。选仓时显示 fork／上游及可见性，预览后若切换目标、账号、模板或正文，旧确认失效。Issue 功能关闭或无法确认身份时保留草稿，不试投其他仓库。

**尊重仓库入口。** 读取目标默认分支的 Issue 模板和 `config.yml`，遵守禁用空白表单、必填、枚举、标题前缀和联系渠道。FD 的 Bug 表单收集 Version、OS、Protocol 与复现；功能建议表单收集场景、方案与 Scope。版本字段不得生成处理批次，`triaged`、`roost:*` 等维护动作不从报告内容推断。查重只向已确认目标主机查询用户可见并同意检索的标题关键词，不发送整段草稿；列开放和关闭候选，不自动合并、评论或阻止新建。

**两条提交路径。** 能完整呈现且不需额外管理动作的表单可在插件内编写；确认页显示主机、仓库、账号、可见性、最终标题和正文。由宿主以 argv 调用 `gh issue create --repo HOST/OWNER/REPO --title TITLE --body-file -`，正文经 stdin 传入。仅当模板元数据能按原语义显式预览并安全应用时才走此路径；不靠 CLI 自行猜模板。不读取附件路径、不自动上传日志、不携带分配、排期、项目或 bot 授权。无法等价呈现模板、要求附件或涉及敏感报告时，转向受信的仓库原生入口；由用户在那里填写并提交，不把草稿拼入 URL。打开网页不算成功，可通过“关联已创建 Issue”提供 URL 并回查身份。

**一次提交的生命周期。** 草稿 → 预览 → 提交中 → 已创建／明确失败／结果待核对。提交前持久化本次尝试并按草稿加锁，使双击、双面板及重启不会重复发送。取得 URL 后回查主机、仓库和 Issue 类型再绑定回执；回查暂不可用时保留候选 URL，不重发。明确被拒（如必填校验失败）返回编辑；超时、响应丢失或进程中断走待核对。按仓库、作者、时间与标题只读找候选，让用户确认具体原件；零结果不证明创建失败。核对前不提供普通重试，不能保证服务端严格幂等。成功后草稿标为已提交，不再参与发送。

**交给谁、怎样回来。** 回执提供“查看原件／在 omp 分析／返回列表”；当前筛选若排除新单，提示原因而不重置筛选。分诊依据仓库实际状态，机器人若已经处理，不再强行标“待分诊”。报告人通过「我创建的」或原链接查看需补材料、复测请求、后续关联 PR 和有证据的版本；回复或关闭仍由用户在有权限的渠道完成。没有回复不可视为验收通过。

**放行条件。** 在专用测试仓库验证 fork／上游选对、FD 风格必填表单、禁止空白、原生网页交接、查到已关闭相似项后仍可报告回归；预览和取消零写入，双击只建一条，创建成功但客户端丢响应时核对原件而非再建。最后以同一编号走通创建、分诊、关联修复、回到报告人复测。禁止用真实 FD 仓库试发测试工单。
